# v12.9.79 — уменьшение памяти браузера

## Замеренная картина (настоящий код упаковки строк)

- Компактная строка каталога ≈ **1,46 КБ** (объект + Float64Array на 143
  расчётных поля = 1,14 КБ). Каталог 200 тыс. SKU ≈ **290 МБ** — это минимум
  текущей архитектуры; убрать его могут только постраничный режим или сервер.
- Вокруг каталога жили дополнительные копии и кэши — их и убираем.

## Что сделано

1. **Воркер фильтра освобождается по простою.** Копия-проекция каталога в
   Web Worker раньше жила до давления MemGuard или смены версии каталога.
   Теперь: 60 с без запросов (`releaseIfIdle`, проверка раз в минуту) и при
   уходе из раздела «Данные» (`UI.go`). Следующий фильтр поднимает воркер
   заново из тех же строк — на результаты не влияет.
2. **`HVC.cross`: Map объектов → Set ключей.** Каждая OE-связь хранила объект
   `{oeNorm, artKey}`, хотя оба значения уже зашиты в ключ
   `oeNorm\u001FartKey`. Теперь хранится только ключ. На плотных OE-графах это
   минус объект на каждую связь (сотни тысяч объектов). Формат записи в
   IndexedDB и GAS не изменён: поля восстанавливаются из ключа при сохранении,
   загрузка собирает тот же Set.
3. **Мягкая уборка по простою.** Раз в минуту, если пересчёт не идёт и heap
   занят > 400 МБ, MemGuard делает мягкий сброс (тарифный кэш, пул
   интернированных строк — раньше не сбрасывался никогда, OE-кэши, воркер),
   не дожидаясь критических порогов 600/820 МБ, за которыми вкладка падает.
   При heap < 200 МБ уровень тревоги сбрасывается, уборка может повторяться.

## Что сознательно не тронуто

- Float64Array расчётных полей: переход на Float32 дал бы экономию ~0,6 КБ/SKU,
  но 24-битная мантисса теряет копейки на миллионных суммах — точность дороже.
- Сам каталог в памяти: его устранение — постраничный режим или сервер
  (отдельные проекты, см. аудит в обсуждении).
