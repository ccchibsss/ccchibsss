# v12.9.60 — прайс поставщика не обогащается сам; горячая строка пересчёта

## Задача (формулировка владельца)

> Прайс поставщика обогащается только новыми файлами, а если нигде не находится —
> то из справочника после добавления файла с весогабаритами.

То есть первый файл (прайс) — это **загрузка**, а не обогащение. Обогащение запускают
файлы-источники (весогабариты, OE-кроссы, названия), остатки добираются из справочника.

## Что было

Импорт прайса `export_Moskow_RUB_RS73404.csv` (124 454 строки, 11 колонок, windows-1251, `;`):

| Этап | Время |
|---|---|
| разбор файла | 6,4 с |
| строки файла | 2,9 с |
| карантин ОВХ | 1,0 с |
| реестр OE | 3,2 с |
| индекс OE | 4,2 с |
| обогащение | 1,0 с → **заполнено 7 из 122 930** |
| стандартные ОВХ | 2,1 с |
| OE по связке | 1,0 с |
| пересчёт и запись | **320,9 с** |
| **всего** | **341,7 с** |

Обогащение на прайсе бессмысленно: в файле нет ни весогабаритов, ни OE, ни категории —
заполнять нечем, а справочник пуст (это первый файл). При этом 320,9 с уходило на
пересчёт, внутри которого профиль показывал:

`strictKey` 28,9 % · GC 11,8 % · разбор CSV 10,6 % · `round` 3,5 % · `num` 2,7 % · `RegExp \s+` 2,6 %

`OzonReference.strictKey` (нормализация NFC + регулярка) вызывался для каждой записи
справочника Ozon на каждую строку: в `detail()` — до четырёх раз на кандидата,
в `resolveCategoryByInternal()` — на весь массив `_idx.entries`.

## Что сделано

1. **Обогащение прайса пропускается.** Если в файле нет ни одного поля-источника
   (`weight`, `net_weight`, `length`, `width`, `height`, `volume`, `oe_numbers`, `oe_list`,
   `oe`, `category`, `subcategory`, `applicability`), шаги «обогащение», «стандартные ОВХ»
   и «связанные строки» не запускаются. В журнал пишется
   `обогащение пропущено: 122 930 строк · в файле нет полей-источников`, в прогресс —
   «обогащение пропущено: в файле нет весогабаритов, OE и категорий».
2. **Кэш `OzonReference.strictKey`** (`_skCache`, сброс на 50 000 записей): функция чистая,
   результат зависит только от строки.
3. **Предвычисленные ключи в справочнике Ozon**: у каждой записи индекса один раз считаются
   `typeKey` (strictKey типа) и `catNorm` (нормированная категория). `detail()` берёт
   `tKey` один раз на кандидата вместо четырёх вызовов, `resolveCategoryByInternal()`
   сравнивает готовые ключи вместо пересчёта по всем записям на каждую строку.

## Известное различие

До правки «стандартные ОВХ» подставляли типовые габариты из справочника **78 строкам**
из 122 930 (0,06 %). Теперь на прайсе этот шаг не выполняется: габариты придут с файлом
весогабаритов, а не найденные там — из справочника при следующем обогащении
или по кнопке «Обогатить сейчас».

## Что осталось в «пересчёте и записи» (144 с)

Строки без весогабаритов всё равно считаются по полной модели и лишь затем помечаются
`systemBlocked`, прибыль обнуляется. Следующий шаг — ранний выход для строк, у которых
заведомо нет входных данных (`!hasShippingData(p)`), с тем же итоговым состоянием полей;
нужен тест на совпадение всех полей строки, поэтому вынесено в отдельную итерацию.
