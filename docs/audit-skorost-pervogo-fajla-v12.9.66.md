# v12.9.66 — почему первый файл грузится долго и что ускорено

Дата: 2026-11-06 · версия приложения: `12.9.66-client+audit.1`

## Что показал журнал пользователя

```
импорт · строки файла: 1 991 мс
импорт · реестр OE: 1 922 мс
импорт · индекс OE: 2 829 мс
обогащение пропущено: 122 930 строк · в файле нет полей-источников
импорт · OE по связке: 713 мс
... память 15–24 % (пересчёт каталога / запись каталога) ...
запись каталога: 1 000 из 122 930 строк
порция записи 2 000–3 000 прервана (1/3): BulkError
```

Видимые этапы (около 7 с) — не главные. Основное время уходит на два процесса,
которые в журнале не разбиты по времени:

1. **пересчёт конвейера** по всем 122 930 SKU (категория → вид → типизация Ozon →
   экономика);
2. **запись каталога** в IndexedDB порциями по 1 000 строк — 123 фиксации
   транзакций на файл, там же браузер и обрывает порцию (`BulkError`).

## Замер до правок (Node-стенд, тот же файл прайса)

Файл `export_Moskow_RUB_RS73404.csv`: 124 454 строки → 122 930 SKU.

| Этап | Время |
|---|---|
| разбор CSV | 5,4 с |
| строки файла / реестр OE / индекс OE / OE по связке / карантин | 12,9 с |
| **пересчёт и запись** | **151,0 с** |
| **итого импорт** | **168,0 с** |

Внутри пересчёта:

| Функция | Время | Доля |
|---|---|---|
| `computeEconomics` (экономика строки) | 70,6 с | 47 % |
| `OzonAuto.applyPreferred` (тип Ozon по названию) | 35,7 с | 24 % |
| `CategoryKindAuto.apply` (вид по названию) | 15,7 с | 10 % |
| `NameCategory.apply` | 6,6 с | 4 % |
| группировка OE (`groupOe`, `rebuildIndex`, `ingest`) | 13,5 с | 9 % |

Внутри `computeEconomics` решатель цен вызывает модель ~5 раз на SKU
(614 668 вызовов `finalizeMarketplaceEco` на 122 930 строк).

## Что сделано (числа не изменились)

1. **Кэш чистых строковых функций.** `CategoryTnved.norm` (внутри
   `normalize('NFKC')` — самая дорогая строковая операция), разбор названия
   `OzonAuto._expand` (30 регулярных замен), токенизация `_tokens` /
   `_literalTokens`, стемминг `OzonAuto._stem` и `CsvNameMatcher.stem/words`,
   нормализация артикула `normArticle` (на файл её вызывают больше 600 000 раз —
   конвейер, `HVC.ensureNorm` четыре раза на строку, ключи групп).
   Кэши ограничены (40–80 тысяч записей) и очищаются при переполнении.
2. **Месячные статьи при нулевых продажах не считаются.** `ecoMonth(v, 0)` всегда
   даёт 0, но в `finalizeMarketplaceEco` эти 19 произведений считались и
   складывались на каждом пробном объекте решателя: 614 668 × 19 = 11,7 млн
   лишних `round`/`num` на файл. Теперь при `sales === 0` сумма равна нулю сразу,
   а месячный объект не строится (он и раньше заменялся на `ZERO_ECO_MONTH`).
3. **Запись каталога порциями по 2 500 строк вместо 1 000** — втрое меньше
   фиксаций IndexedDB на первом импорте (49 против 123) при той же памяти порции.
   В журнал добавлена строка `запись каталога: N строк за X мс` — видно вклад
   диска в общее время.
4. `.slice()` у кэшированных массивов токенов: `CsvNameMatcher.guess` делает
   `shift()` у результата `_tokens`, поэтому кэш отдаёт копию.

## Проверка, что цифры не изменились

Снимок ~80 полей на строку (цена, себестоимость, все статьи, ЧП/ед., маржа, ROI,
безубыток, целевая цена, `priceForApi`, плоские поля площадок, статус, качество
данных, категория, вид, тип Ozon и его источник, причины) до и после правок:

| Набор | Строк | Расхождений |
|---|---|---|
| прайс (без габаритов) | 4 975 | **0** |
| прайс + весогабариты | 23 821 | **0** |
| прайс, расширенная выборка | 19 918 | **0** |

Синтаксис app-блока — `node --check` OK.

## Что осталось и почему

После правок 100 % времени — это сам расчёт: ~460 мкс на SKU в экономике
(решатель цен вызывает модель ~5 раз) и ~180 мкс на типизацию названия.
Дальнейшее ускорение без изменения чисел возможно двумя путями, оба — отдельные
итерации:

1. **Пул воркеров** для экономики и типизации: строки не зависят друг от друга,
   на 4 ядрах это 2,5–3× (нужно передавать в воркер настройки и тарифы, а обратно —
   только расчётные поля).
2. **Точечный пересчёт после справочных файлов**: сейчас файл весогабаритов
   пересчитывает весь каталог, хотя меняется только часть строк (порог
   `smallDelta` — 2 % каталога). На их файлах доля изменённых строк выше порога,
   поэтому включается полный пересчёт.

## Что смотреть в журнале при следующем импорте

- `импорт: … пересчёт и запись …` — общая раскладка по этапам;
- `запись каталога: N строк за X мс` — новый замер записи;
- отсутствие `порция записи … прервана (…/3): BulkError` — признак, что порция
  2 500 строк проходит без обрыва.
