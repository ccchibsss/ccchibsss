# Импорт v12.9.84 → v12.9.85 — расширенное обогащение SKU прайса

Продолжение v12.9.83 (первый файл — прайс, дальше только обогащение по нему).
По выбору пользователя расширены все три направления обогащения.

## 1. Ключи поиска SKU прайса
Раньше строка файла сопоставлялась с прайсом только по артикулу+бренду и по
артикулу. Теперь, если артикул не совпал, ищется **уникальный** SKU прайса:
- по OE-номерам файла (колонки OE) среди OE текущего прайса.

Поиск по аналогам не используется (правка пользователя в v12.9.85): ключей
только два — артикул+бренд и OE-номер. Индекс OE строится один раз лениво по
строкам каталога на старте импорта. OE, принадлежащий нескольким SKU, не
используется (неоднозначно).

## 2. Поля и защита идентичности
- При OE/аналог-сопоставлении артикул и бренд файла **не затирают** артикул и
  бренд SKU прайса — файл только обогащает строку; сам артикул файла
  добавляется в `analog_list` найденного SKU.
- Остальные поля применяются обычным механизмом импорта: списки OE и
  применимость накапливаются, габариты защищены от затирания нулём,
  штрихкод/картинка/категория/ТН ВЭД и пр. — как раньше.

## 3. Доноры внутри прайса
Без изменений механизма, но теперь он работает и на OE-сопоставленных строках:
после импорта затронутые и связанные строки проходят `HVC.enrichAsync`
(название, применимость, категория/ТН ВЭД, габариты, штрихкод, картинка от
доноров с общими OE внутри прайса).

## Отчётность
В итоге импорта: «сопоставлено по OE прайса: N».

## Проверка
- Стенд на настоящих `codeList/mergeCodeLists/normArticle` из приложения:
  OE-1 → свой SKU; OE, общий для двух SKU, → нет сопоставления; неизвестный
  ключ → нет сопоставления.
- `node tests/run-tests.js` — OK; `node --check` — OK.
