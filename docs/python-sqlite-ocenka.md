# Можно ли все расчёты делать на Python + SQLite — оценка (v12.9.100)

**Короткий ответ: да, расчётное ядро переносится полностью. Всё приложение —
нет (и не нужно): интерфейс, Dexie и GAS остаются на своих местах.**

## Доказательство: рабочий прототип

`tools/python_sqlite_poc.py` (только стандартная библиотека Python):
создаёт SQLite-базу (products/settings/eco_results), загружает золотые
12 SKU, считает экономику Ozon и сверяет с эталоном приложения.

Результат: **0 расхождений** — итоги, прибыль, маржа и ROI совпали по всем
12 SKU до копейки; безубыток совпал с целочисленной точностью решателя
приложения (ручная колонка эталона дробная: 14376.01 → 14377 ₽).
Налоги (УСН 6%, УСН+НДС 5%, ОСНО с вычетом) и ступени логистики WB
совпали с ручными кейсами аудита.

## Почему ядро переносимо

Расчётный блок (налоги, 5 площадок, решатель цен, тарифы) при аудите
оказался чистым: в ~2400 строках ядра **0 обращений к document/window/
localStorage/fetch**. Зависимости только две: глобальные настройки
(S.settings → таблица settings) и число SKU (S.rows.length → COUNT(*)).
Функции портируются почти 1-в-1; округление Excel-стиля повторяется
через Decimal.

## Производительность

Решатель приложения делает 20–40 пробных расчётов на SKU. На Python
124 тыс. SKU × 1 площадка — минуты в один поток (приемлемо для пакетного
режима); ускоряется аналитическим решателем для линейных участков,
кэшем тарифов и multiprocessing. SQLite на таких объёмах (сотни тысяч
строк, индексы по article/brand/OE) работает без вопросов; обогащение
групповыми запросами в SQL будет быстрее нынешних ручных индексов в JS.

## Риски

1. **Двойная реализация** — JS и Python начнут расходиться. Лечится только
   общими золотыми фикстурами: те же CSV эталонов гонять в обоих тестах
   (инфраструктура уже есть: фикстуры 12 SKU + тесты приложения).
2. **Модель развёртывания меняется**: браузерное приложение работает
   офлайн одним файлом; Python требует локального запуска/сервера.
3. Округления float vs Decimal: в прототипе использован Decimal —
   совпало; держать это правилом.

## Рекомендация

Не переписывать приложение, а вынести в Python+SQLite **пакетный контур**:
ночной/ручной пересчёт каталога, тяжёлое обогащение, сверка экономики
(второй независимый расчёт — как аудит). Браузер остаётся интерфейсом и
оперативным калькулятором. Если позже понадобится серверная версия —
ядро уже будет готово и покрыто эталонами.
