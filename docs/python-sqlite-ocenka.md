# Можно ли все расчёты делать на Python + SQLite — оценка (v12.9.100)

**Короткий ответ: да, расчётное ядро переносится полностью. Всё приложение —
нет (и не нужно): интерфейс, Dexie и GAS остаются на своих местах.**

## Доказательство: рабочий прототип

`tools/python_sqlite_poc.py` (только стандартная библиотека Python):
создаёт SQLite-базу (products/settings/eco_results), загружает золотые
12 SKU, считает экономику Ozon и сверяет с эталоном приложения.

Результат: **0 расхождений** — итоги, прибыль, маржа и ROI совпали по всем
12 SKU до копейки; безубыток совпал с целочисленной точностью решателя
приложения (ручная колонка эталона дробная: 14376.01 → 14377 ₽).
Налоги (УСН 6%, УСН+НДС 5%, ОСНО с вычетом) и ступени логистики WB
совпали с ручными кейсами аудита.

## Почему ядро переносимо

Расчётный блок (налоги, 5 площадок, решатель цен, тарифы) при аудите
оказался чистым: в ~2400 строках ядра **0 обращений к document/window/
localStorage/fetch**. Зависимости только две: глобальные настройки
(S.settings → таблица settings) и число SKU (S.rows.length → COUNT(*)).
Функции портируются почти 1-в-1; округление Excel-стиля повторяется
через Decimal.

| Зона | Строк JS | Перенос |
|---|---|---|

| Формулы ExprLang, веса, кратность | ~400 | Да |

| Импорт CSV/XLSX | ~1600 | Да: csv — stdlib, XLSX — openpyxl |
| Экспорт (Ozon-шаблон, XLSX/CSV) | ~1700 | Да: openpyxl |
| Дашборд/агрегаты | — | Да, частично SQL-запросами |
| UI, таблица, воркеры, Dexie | ~половина файла | Нет — остаётся браузер |
| GAS-бэкенд (Apps Script) | ~3950 | Нет — это уже сервер Google |

## Производительность и память (замер на 124 000 синтетических SKU)

Стенд: упрощённая модель Ozon (комиссия/перевод/налог/фикс-статьи +
аналитический решатель), один поток, машина песочницы:

| Операция | Результат |
|---|---|
| Вставка 124k строк в SQLite | 0.85 с (~145 тыс. строк/с) |
| Расчёт с решателем безубытка и целевой цены | 3.9 с (~31 тыс. SKU/с) |
| Агрегат SUM/AVG по всем результатам | 20 мс |
| Построение OE-групп (GROUP BY + HAVING) | 21 мс |
| Размер базы с результатами и индексами | 22.8 МБ = **184 байт/SKU** |
| Пик RAM всего процесса | 112 МБ (включая списки в памяти; при потоковой обработке — меньше и не растёт от каталога) |

Для сравнения, браузерное приложение (замеры из docs v12.9.54–58): heap
после пересчёта ~4.8 КБ/SKU (176 МБ на 30 тыс. строк), на 217 тыс. SKU
вкладка исторически упиралась в ~1.3 ГБ и лимиты браузера. SQLite хранит
данные на диске и подкачивает страницами: RAM почти плоская при любом
размере каталога, предел — размер диска.

Честная оговорка: стенд считает упрощённую модель одной площадки.
Полный перенос (5 площадок, тарифы, категории, политики) будет медленнее —
оценка 5–15 тыс. SKU/с в один поток, что сопоставимо с нынешним пайплайном
(~90–120 мкс/строка по замерам v12.9.56) или быстрее; плюс multiprocessing
даёт почти линейное ускорение по ядрам, а SQL-агрегаты и обогащение
групповыми запросами заменяют полные проходы по каталогу в JS.

## Что это даёт по расчётам

- **Точность**: деньги считаются через Decimal — нет двоичных артефактов
  float (в JS приходится лечить «грязные» .4999… эвристиками округления).
- **Проверяемость**: любой итог пересчитывается независимым SQL-запросом
  за миллисекунды; второй независимый расчёт = постоянный аудит первого.
- **Целостность**: транзакции (нет полузаписанного каталога), уникальные
  ключи и внешние ограничения на уровне базы, а не кода.
- **Обогащение**: OE-группы, кластеры и джойны файлов поставщиков — это
  GROUP BY/JOIN, а не ручные индексы в памяти вкладки.

## Риски

1. **Двойная реализация** — JS и Python начнут расходиться. Лечится только
   общими золотыми фикстурами: те же CSV эталонов гонять в обоих тестах
   (инфраструктура уже есть: фикстуры 12 SKU + тесты приложения).
2. **Модель развёртывания меняется**: браузерное приложение работает
   офлайн одним файлом; Python требует локального запуска/сервера.
3. Округления float vs Decimal: в прототипе использован Decimal —
   совпало; держать это правилом.

## Рекомендация

Не переписывать приложение, а вынести в Python+SQLite **пакетный контур**:
ночной/ручной пересчёт каталога, тяжёлое обогащение, сверка экономики
(второй независимый расчёт — как аудит). Браузер остаётся интерфейсом и
оперативным калькулятором. Если позже понадобится серверная версия —
ядро уже будет готово и покрыто эталонами.
