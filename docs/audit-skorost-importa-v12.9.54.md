# Скорость импорта и записи крупного каталога — v12.9.54

Дата: 2026-11-05. Основание: журнал браузера пользователя для каталога 217 448 SKU.

Память всё время на 94–100 % heap, `MemGuard` срабатывал каждые несколько секунд.

Две строки в журнале объясняют львиную долю:

```
[UC] запись каталога: 217 448 SKU · 969 391 мс · режим economy · записано 217 448
[UC] запись каталога: 217 448 SKU · 341 432 мс · режим economy · записано 28
```

Вторая запись — 28 строк за 341 секунду. Данные тут ни при чём: время уходит на подготовку и на обслуживание уже раздутого heap, а не на сам IndexedDB.

## 2. Замеры на стенде (Node + fake-indexeddb, 30 000 строк)

Стенд: приложение целиком (`index.html`, все модули), заглушки DOM, `fake-indexeddb`,
одинаковый синтетический каталог (артикул, бренд, категория, цена, себестоимость,
продажи, весогабариты). Абсолютные числа отличаются от браузера, отношения — нет.

| Операция | v12.9.53 | v12.9.54 | Δ |
|---|---|---|---|
| Полный пересчёт (первый) | 23 907 мс | 19 639 мс | −18 % |
| Полный пересчёт (повторный) | 19 601 мс | 16 775 мс | −14 % |
| Запись каталога 30 000 строк | 2 204 мс | 1 707–2 031 мс | −8…−23 % |
| Точечный пересчёт 30 строк | 1 349 мс | 919 мс | −32 % |
| Подстановка ОВХ (дельта + `skipGroups`) | ≈1 349 мс | 730 мс | −46 % |

Профиль CPU (30 000 строк, `--cpu-prof`) — где реально живёт время:

| Доля | Функция |
|---|---|
| 21,3 % | `finalizeMarketplaceEco` (месячные суммы по 19 статьям на каждую пробную цену) |
| 6,2 % | `_formatNumber` (Intl.NumberFormat в текстах строк) |
| 5,6 % | garbage collector |
| 5,5 % | `normTariffPath` (нормализация пути категории; 12 кандидатов на строку) |
| 5,5 % | `computeEconomics` |
| 4,3 % | `evaluateYm` |
| 4,0 % | `calcMarketplacesEconomics` |
| 3,0 % | `packEco`, `month`, `cheapFbsTariff` |

То есть пересчёт — это честный расчёт пяти площадок с целочисленным решателем
по каждой строке. Ускорить его в разы можно только изменив объём расчёта.

## 3. Что исправлено в 12.9.54

1. **Неиспользуемые индексы IndexedDB.** Приложение нигде не выбирает товары по
   `article`, `brand`, `category`, `abcClass` — только по первичному ключу и полным
   перебором. Но каждый `bulkPut` обновлял четыре индекса. Схема переведена на
   `products: '++id'` (новая версия базы 6, данные сохраняются).
2. **Порция записи 1000 → 2000 строк.** Вдвое меньше фиксаций IndexedDB. Обрыв
   по-прежнему стоит одной порции: повтор идёт по 300 строк.
3. **`MemGuard` больше не сбрасывает кэши чаще раза в 10 секунд.** Раньше на каждой
   четверти порции пересчёта чистился кэш тарифов и освобождался воркер фильтра —
   следующий же SKU пересобирал индекс тарифов заново, а к концу прохода каталог
   заново копировался в новый воркер. Повышение уровня 1 → 2 срабатывает всегда.
4. **Точечный пересчёт не перебирает весь каталог.** Автосверка ОВХ вызывала полный
   `runPipeline` ради 28 изменённых строк: перебор 217 000 строк, пересборка
   OE-групп, ABC/XYZ и фильтра. Теперь при известном наборе изменённых строк
   (`smallDelta`) неизменённые строки пропускаются целиком, а группы OE не
   пересобираются (ключи артикул+бренд от ОВХ не зависят).
5. **Кэш нормализации пути категории.** `normTariffPath` — чистая функция, её
   результат одинаков для тысяч SKU одной категории: теперь кэшируется по исходной
   строке (потолок 20 000).
6. **Диагностика в журнале:** тайминги записи разделены на «каталог» и «служебные
   таблицы», добавлено время сохранения реестров Каталога V, в итог импорта —
   размер heap и байты на SKU.

## 4. Почему этого мало: память

Замер на 30 000 строк (после пересчёта, принудительный GC): **6 178 байт на строку**.

| Что | Байт на строку | На 217 448 SKU |
|---|---|---|
| `p.mp` — экономика пяти площадок | 2 401 | ≈ 500 МБ |
| собственные поля строки (51 ключ) | ≈ 3 400 | ≈ 700 МБ |
| `_c` — Float64Array расчётных чисел | 184 | ≈ 40 МБ |
| служебные (`_sources`, доказательства OE) | 170 | ≈ 35 МБ |

`p.mp` нигде не сохраняется — он целиком пересчитывается при каждом запуске. При
этом держится в памяти по всем строкам, потому что нужен дашборду (сравнение
площадок), таблице и выгрузке. Именно эти ≈1,3 ГБ и держат вкладку на 94–100 % heap,
а на таком heap пересчёт и запись идут в 10–40 раз медленнее, чем без давления GC
(запись 28 строк за 341 с — про это).

Пробная замена массива значений `packEco` на `Float64Array` **не помогла** (замер:
6 675 Б/строка против 6 177) — типизированный массив сам по себе дороже, а V8 и так
хранит чисто числовой массив без упаковки. Правка отменена, чтобы не менять
поведение без выигрыша.

## 5. Следующий шаг (предложение)

Единственный способ ускорить в разы — сократить объём данных в памяти, а не
микрооптимизировать расчёт:

1. **Держать `p.mp` только для выбранной площадки**, а по остальным — компактную
   сводку (прибыль, маржа, безубыток, рекомендация уже есть плоскими полями
   `profitWB`, `marginOzon`, `beYM`…). Нужно перевести на плоские поля дашборд
   (агрегат «по площадкам»), таблицу сравнения и проверку доступности.
   Ожидание: −1,5…−2 КБ на строку, то есть ≈ −350 МБ на 217 000 SKU.
2. **Не хранить производные тексты в базе** (`recommendation`,
   `tariffQuoteReasons`, `economicsDataQuality`, `policyReason`…) — они
   пересчитываются при запуске. Ожидание: запись и база легче на ≈35 %.
   Требует, чтобы старт не пересчитывал каталог целиком, иначе тексты будут
   пустыми до конца пересчёта.
3. **Пропускать полный пересчёт при старте, если входные данные не менялись**
   (подпись: версия, тарифная модель, настройки, тарифы, правила). Сейчас каждое
   открытие вкладки на 217 000 SKU — это ещё один полный проход. Упирается в то же
   `p.mp`: без ленивого `mp` пропустить пересчёт нельзя.

Пункты 1–3 связаны и делаются одной итерацией с проверкой выгрузок на стенде
(матрица формул калькулятора и общая выгрузка).
