# Проверка производительности импорта и экспорта

Проверен текущий код ветки вместе с новым data-only export (PR #93). Первоначальные находки приведены ниже; фактический статус внедрения и ограничения — в последнем разделе. Замеры ниже локальные синтетические; файлы пользователя и Windows/PyInstaller не проверялись.

## 1. Чтение больших файлов: убрать полные промежуточные копии (P0)

`engine/uc_engine.py:_raw_table` материализует весь XLSX через list(iter_rows), а CSV — через list(csv.reader). `parse_file_bytes` добавляет all_rows, срезы таблицы и полный список (session, idx, JSON) для executemany. Режим openpyxl read_only сам по себе здесь не делает обработку потоковой.

Предложение: ограниченный буфер первых строк для определения заголовков, затем итератор записей и подготовка/вставка небольшими пакетами. Не держать одновременно всю исходную таблицу и все JSON-записи. Сохранить существующие правила выбора заголовков, пропуска пустых строк, кодировок, типов артикулов, дат и дубликатов заголовков. Незавершённую parse_session не публиковать; предусмотреть cleanup/TTL и явную отмену. Бounded transactions не должны выдавать частичный файл как успешно разобранный.

## 2. SQL → браузер → таблица: лишний круг данных (P0/P1)

`PyEngine.parseFile` получает все страницы как объекты и накапливает out. `Import.read` затем строит из этих объектов полную матрицу table и ещё body. Для 961350 строк передаются все исходные строки, хотя каталог прайса — 122941 SKU.

Ближайшая оптимизация: формировать строки для маппинга постранично, без промежуточного полного массива объектов. Архитектурная: хранить разобранный файл в SQL, в браузер отдавать заголовки/5 строк предпросмотра; применять подтверждённый маппинг в Python пакетами. Это крупная работа с обязательной проверкой browser/SQL parity: совпадения article/brand/OE, неоднозначности, карантин, пользовательские колонки, правило первого прайса и запрет новых SKU при обогащении. Нельзя просто заменить на normalized products import.

## 3. Пагинация parse_rows: индекс есть, OFFSET мешает (P1)

Текущий запрос `/parse/rows`: WHERE session=? ORDER BY idx LIMIT ? OFFSET ?. PK(session,idx) уже есть. Последующие страницы снова проходят предыдущие индексные записи.

Прямой локальный probe: SQLite :memory:, 961350 строк с коротким одинаковым JSON, страницы по 5000 (193 страницы), без HTTP/JSON-декодирования:

| Запрос | Все страницы |
| --- | ---: |
| LIMIT/OFFSET | 5.836 s |
| WHERE session=? AND idx>=? ORDER BY idx LIMIT ? | 0.405 s |

EXPLAIN: первый поиск только session; второй — session и диапазон idx. Это около 14.4x только на этом синтетическом участке, НЕ на всём импорте. Последовательные idx создаются enumerate(table); можно использовать offset как нижнюю границу при сохранении контракта непрерывной готовой сессии. Нужны тесты первой/последней/пустой страницы, повреждённой/незавершённой сессии и фактического HTTP.

## 4. Data-only export: потоковый CSV и XLSX (P0)

Сейчас Python `export_data_only` декодирует все app_catalog_chunks в общий rows. CSV добавляет StringIO, итоговую строку и bytes; `_send_bytes` при gzip создаёт ещё сжатую копию. Клиент получает весь файл через response.blob(). XLSX-писатель накапливает rows_xml, затем общий XML и ZIP. В браузерном XLSX дополнительно создаются общая матрица, worksheet, итоговый array и Blob.

Предложение: двухпроходное чтение канонического snapshot: (1) множество присутствующих полей/количество строк, (2) запись значений в файл порциями. Для XLSX — потоковая запись sheet XML в ZIP, не список XML-строк; только текст/числа, без формул и подстановок. Для CSV — TextIOWrapper над временным файлом, без полной строки в RAM. Скачивание готового файла через job/token с ограниченным TTL и серверной потоковой передачей вместо bytes-ответа; без токенов авторизации в URL. В браузерном режиме worker/yield решает отзывчивость, но не автоматически устраняет все копии SheetJS.

Согласованность нельзя потерять: app_catalog chunks старых ревизий сейчас удаляются при новом commit. Нужна закреплённая read-транзакция на время копирования snapshot или отдельное хранилище export job. Длинная read-транзакция может удерживать WAL; не держать её на время медленного скачивания файла. Контроль диска, cleanup на error/cancel, лимит параллельных jobs обязательны.

## 5. Полное сохранение перед каждой data-only выгрузкой (P1)

`DataOnlyExport.run` безусловно вызывает persistNow в SQL. `saveSqlCatalog` снова отправляет весь каталог частями по 1000 строк. Это безопасно для актуальности, но повторный экспорт неизменённого каталога может стоить полного прохода сериализации/записи.

Предложение: надёжная dirty/revision-модель для row edits и метаданных, дождаться текущего сохранения, затем выгружать конкретную подтверждённую ревизию. Не пропускать сохранение по одному catalogVersion: часть изменений производится in-place. До аудита всех путей редактирования оставлять полное сохранение как безопасное поведение.

## 6. Планирование SQLite писателей (P1)

HVC уже имеет очередь записи и ограниченное ожидание. Но запись app_catalog идёт тремя workers, parsing и другие endpoints также пишут в ту же базу. WAL не превращает SQLite в многописательную БД.

Предложение: общая управляемая очередь тяжёлых записей/планировщик, небольшие транзакции, подготовка JSON вне write-lock; метрики времени ожидания и длительности транзакций. Проверить lock ordering с Ozon cache lock и HVC lock. Не заменять решение бесконечным timeout или повторной отправкой POST: это маскирует блокировки и может повторить побочные эффекты.

## 7. Подготовка Ozon/HVC и прогресс (P1/P2)

Ozon справочник уже загружается один раз на pipeline, но JSON.stringify полного графа и построение полного IdentityGuard остаются. Возможна дальнейшая работа с каноническими SQL-справочниками по ревизии и предрасчитанным unsafe OE. Нельзя ограничивать identity только текущими 600 SKU: потеряются глобальные конфликты.

Строки импорта показывают общий прогресс, тогда как внутри первого пакета идут разные запросы. Нужны отдельные этапы/таймеры: upload reference, model build, name/category/Ozon, политики, сохранение и скачивание. Полоса Prog сейчас растёт по таймеру и не отражает долю обработанных данных — заменить на определённый прогресс либо неопределённый индикатор с честным названием этапа.

## Порядок внедрения и проверки

1. Диапазонная пагинация, удаление полного списка JSON перед executemany, метрики стадий — небольшие независимые изменения.
2. Потоковый SQL data-only CSV/XLSX и export jobs — главный выигрыш по памяти экспорта.
3. Буферизованный parser и сокращение browser roundtrip.
4. SQL применение маппинга и ревизионный reuse — отдельный проект с полным parity-набором.

Для каждого этапа: 122941 SKU прайса, файл обогащения 961350 строк; разные ширины таблицы и объёмы OE; время wall-clock, peak RSS Python/heap браузера, байты HTTP, число запросов, ожидание SQLite, временный диск/WAL, число строк/колонок результата. Сравнение CSV ячеек/XLSX значений, ведущие нули, даты, кириллица, формульные префиксы, custom arrays/objects, hidden rows, отмена/ошибка/конкурентное изменение. В data-only пути запретить вызовы economics/recalc/typing тестами. Обогащение при импорте остаётся без экономики; база не сбрасывается.


## Статус внедрения в этой ветке

Внедрены:
- диапазонное чтение parse_rows с тем же HTTP-контрактом offset/limit;
- итератор CSV/openpyxl XLSX и ограниченный буфер первых строк для заголовка;
- подготовка JSON на временный диск до write-lock; вставка пакетами 1000 в атомарную parse_session, без полной JSON-копии RAM;
- прямое накопление матрицы для SQL-маппинга, без полного промежуточного массива объектов;
- общая очередь тяжёлых writes для parse publication, app_catalog mutations и HVC; чтение app_catalog не ставится в эту очередь;
- двухпроходный дисковый snapshot нового data-only экспорта, потоковый CSV/XML-in-ZIP, освобождение SQL read snapshot до форматирования/скачивания;
- передача HTTP-файла блоками с диска; проверка ожидаемой ревизии; ограничение двух генераций;
- File System Access API для прямого SQL скачивания/порционного браузерного CSV с обычным Blob-скачиванием для несовместимых браузеров;
- браузерный XLSX заполняется пакетами, не общей матрицей; yield/cancel/version checks;
- полоса больше не растёт от таймера; метки реальных этапов SQL обогащения и сохранения.

Замер `python engine/tests/perf_io_probe.py --rows 40000` (tracemalloc, SQLite :memory:, 4 колонки): старый CSV-алгоритм 40.95 MiB / 1.840 s; дисковый CSV 1.64 MiB / 4.437 s. CSV SHA-256 совпадает побайтно. Это примерно 25x меньше traced Python allocations ценой более долгой сборки на этом небольшом наборе. Ускорение всех операций НЕ заявляется: приоритет — ограничение памяти больших файлов. Предыдущий probe потокового XLSX: 1.50 MiB / 11.443 s (до изменения буферизации snapshot с строки на часть); точного сравнения со старым XLSX не выполнялось. Peak RSS/браузерная память не измерялись.

Осталось (не называть внедрённым):
- полный перенос применения подтверждённого маппинга из браузера в Python;
- отказ от browser materialization всего файла: матрица всё ещё целиком нужна существующему мастеру;
- безопасный reuse сохранённой ревизии без полного save: нужна ревизионная/dirty-модель всех in-place edits;
- потоковый stdlib XLSX fallback без openpyxl (существующий fallback всё ещё материализует лист);
- перенос SheetJS сериализации в worker; браузерный XLSX всё ещё держит worksheet/ZIP;
- долговечные фоновые parse/export jobs с серверной отменой/TTL (сейчас lifecycle файлов привязан к запросу);
- единый планировщик абсолютно всех write endpoints: добавленная очередь покрывает тяжёлые parse/app_catalog/HVC операции, но не каждый существующий endpoint;
- полное индексирование Ozon reference/IdentityGuard по ревизии вместо построения полной модели.

Эти пункты нельзя безопасно заменить отключением проверок, бесконечными timeout, browser fallback для SQL или частичным незаметным импортом. Текущий объём уменьшает пиковые копии и устраняет OFFSET-проходы, не меняя правил сопоставления SKU и не включая экономику при импорте.

Итог проверки текущего набора: 264 tests OK (54.317 s), node tests/run-tests.js OK, 6 inline scripts syntax OK, py_compile и git diff --check OK. Дополнительные тесты: реальный HTTP с первой/последней/пустой диапазонной страницей и файловым CSV-ответом; поздняя ошибка парсера до публикации; rollback SQLite после ошибки на 1001-й строке; файловый XLSX без полноразмерного XML builder; сохранение новой ревизии до чтения уже сформированного файла; прямая запись браузера на диск, отмена выбора файла и abort writer при ошибке.
