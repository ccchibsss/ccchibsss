# Браузерные таблицы источников

Обычная загрузка через «Импорт» в браузерном режиме теперь сначала сохраняет
каждый CSV/XLSX/XLS/ODS в отдельный набор строк IndexedDB. Файл после загрузки
не нужен для повторного открытия маппинга. В разделе импорта есть кнопка
**«Таблицы источников»**: открыть маппинг либо удалить только исходную таблицу.
Удаление не отменяет уже внесённые изменения каталога. Исходники не являются
резервной копией: браузер может очистить хранилище, действует дисковая квота.

## Обработка

- Отдельная БД `UC_BrowserImportSources` (текущая schema v4). Новые данные
  хранятся страницами `rowPages`, старые построчные `rows` остаются читаемыми.
  `sources` содержит версию формата и число строк. `runs` и `catalogRuns`
  описывают индексы, их новые данные лежат в `keyPages`; `keys`/`catalogKeys`
  сохранены для совместимости и очистки старых данных. Исходные значения не
  изменяются при применении маппинга.
- CSV читается блоками 256 КиБ. Перед следующим блоком ожидается запись в
  IndexedDB; транзакции записи — до 1000 строк. Предпросмотр — до 200 строк,
  без разреженного массива размером во весь файл.
- XLSX разбирается во Worker. Главный поток запрашивает очередные <=1000 строк
  только после сохранения предыдущих. **SheetJS всё ещё держит распакованный
  лист в памяти воркера**; это не потоковый XLSX-парсер.
- Перед изменением каталога полный проход по источнику строит временный
  дисковый индекс нормализованных ключей и сигнатур. Конфликт в последнем
  пакете блокирует также первый вариант — произвольного «первого совпадения» нет.
  Проверка бренда и стандартных полей соответствует прежнему массивному пути.
  OE, применимость и пользовательские поля не создают такой конфликт.
- Применение читает по 4000 исходных строк и запрашивает конфликты только для
  текущего пакета. Сам merge/OE-накопление/транзитивное обогащение остаётся прежним.
  Первый прайс загружается без обогащения, следующие файлы обогащают его без
  создания новых SKU; экономика при импорте не рассчитывается.
- Полностью построенный индекс сохраняется для повторного Apply того же
  маппинга. Ключ кеша включает версию алгоритма, режим ключа, заголовки,
  выбранные поля/колонки, виртуальные значения и состав стандартных полей.
  Незавершённый индекс не используется повторно. После успешного построения
  нового индекса старые индексы источника удаляются; удаление источника удаляет
  также его индекс. Исходник остаётся доступным.
  Отмена/ошибка чтения удаляет недописанный источник; если удаление не удалось,
  запись `loading` можно удалить в списке источников. После аварийного закрытия
  вкладки недописанные источники также могут остаться в списке, их нельзя применить.
- Режим SQL не создаёт эти таблицы и не может применять сохранённый браузерный
  источник. SQL-импорт и SQLite-хранилище работают прежним отдельным путём.

## Границы

Это устранение полного массива исходного файла и полного RAM-индекса его
конфликтов, **не полностью дисковый каталог**. `S.rows`, каталог V и OE-накопители остаются в RAM. Для последующего
обогащения обычного IndexedDB-источника целевые индексы вынесены на диск
(подробности ниже); первый прайс пока использует прежние RAM-индексы. Два CSV по миллиону строк
больше не требуют держать оба полных исходных массива, но миллион уникальных
SKU всё ещё может превысить доступную память браузера. Быстрее по времени
не обещается: добавляется первичная запись и дисковый preflight.

Почтовые вложения, программный `applyRows` и отдельный мастер обновления
прайса не перенесены на эту схему. Для повторяемого браузерного сценария с
несколькими большими файлами используйте обычный «Импорт» и список источников.

## Дополнительная оптимизация и сериализация операций

Обычное чтение импорта, Apply, удаление источника и переключение browser/SQL
используют единую блокировку. Повторный запуск в одной вкладке отклоняется.
При наличии Web Locks конфликтующая операция в другой вкладке отклоняется
через `ifAvailable`, без скрытой очереди и последующего применения устаревшего
маппинга. Ошибка внутри callback не приводит к повторному выполнению операции.
В браузерах без Web Locks защита ограничена одной вкладкой. Это не глобальная
блокировка всех редакторов каталога, фоновых действий или отдельных мастеров.

Список `touched` теперь содержит каждую изменённую строку не более одного раза,
даже если для неё во входном файле тысячи OE. Финальный список изменений
строится без промежуточного объединённого массива из трёх списков; повторный
Set поверх уже уникального touched убран. Сами правила накопления OE и
транзитивного обогащения не изменены.

**Пока не реализованы:** дисковый целевой каталог вместо `S.rows` и публикация
всего Apply одной транзакцией. Для ошибок/прерванного Apply теперь есть
специальная контрольная точка и атомарное восстановление (ниже). Прогон в
настоящем браузере на 2×1 млн строк пока не выполнен.

## Контрольная точка браузерного Apply

Схема основной БД повышена до v7: добавлена таблица `applyUndo` с индексами
`table` и `[table+pos]`. SQL этот механизм не использует. Это не старый механизм
восстановления исторического снапшота: откатывается только конкретный
незавершённый Apply, отмеченный `meta.browserApplyCheckpoint`.

1. После проверки готовности хранилища сохраняются текущие изменения до импорта.
   При ошибках товаров, вспомогательных таблиц или HVC применение не начинается.
2. В одной транзакции копируются `products`, `products_stage`, `meta`, категории,
   правила, исключения, история импортов и четыре таблицы HVC. Чтение и запись
   резервной копии идут пакетами <=1000 записей, без второго полного JS-массива.
   Маркер публикуется в этой же транзакции только с полной копией и счётчиками.
3. Дальше работает существующий пайплайн. Его операции сохранения с проверкой
   `assertCatalogFresh` также проверяют владельца маркера; другая вкладка не
   может штатно перезаписать каталог/HVC до завершения или восстановления.
4. После сохранения и финальной проверки ошибок/отмены удаляются маркер и
   резервная копия одной транзакцией. Только затем очищается входной preview
   и источник помечается применённым.
5. Ошибка/отмена до подтверждения вызывает восстановление всех перечисленных
   таблиц **одной транзакцией**. Перед этим автосохранение грязной RAM блокируется
   через `_bootReady=false`. После восстановления страница перезагружается,
   чтобы не оставить устаревшие ссылки, карты HVC и вычисленные кеши в памяти.
   Исходные файлы в отдельной БД источников не откатываются и не удаляются.
6. После аварии/закрытия страницы загрузка каталога обнаруживает маркер и
   предлагает восстановление. Отказ останавливает запуск и запись; он не
   принимает частично записанный каталог за завершённый. При Web Locks живой
   импорт в другой вкладке блокирует восстановление. Без Web Locks перед
   подтверждением необходимо закрыть другие вкладки приложения.

Восстановление сначала проверяет полноту резервной копии. Любая ошибка,
включая ошибку после очистки части таблиц, отменяет всю транзакцию восстановления:
текущее состояние и контрольная точка остаются для следующей попытки. Если
автооткат не удался, работа блокируется до перезагрузки/восстановления.

### Границы и стоимость

- Это **восстанавливаемый Apply**, не изолированная публикация всего результата:
  промежуточные транзакции пайплайна могут уже находиться на диске до commit.
  После аварии их нельзя использовать без решения о восстановлении.
- Нужна дополнительная дисковая квота примерно под копию перечисленных таблиц;
  создание контрольной точки и сохранение исходного состояния добавляют время.
  Недостаток места при создании копии останавливает импорт до изменения данных.
- Все будущие записи каталога должны сохранять проверку владельца. Блокировка
  не покрывает произвольные консольные записи, сторонние старые версии приложения
  и все редакторы несвязанных таблиц.
- Браузерный volatile-режим без IndexedDB не допускает безопасный Apply.
- Удалённая репликация HVC через GAS не запускается из `HVC.save` во время
  незавершённого Apply: локальный rollback не может отменять сетевые действия.
  Следующее обычное сохранение вне Apply использует прежнюю репликацию.
- Контрольная точка охватывает IndexedDB, а не произвольные внешние API,
  localStorage или незаписанные очереди интерфейса. После отката RAM перечитывается.

## Дисковые целевые индексы сопоставления

Для обычного браузерного источника, применяемого к существующему прайсу,
`BrowserCatalogLookup` строит временные индексы в БД источников (schema v2):
`catalogKeys` по `[run+kind+key]`, `catalogRuns` по источнику. Виды ключей:
артикул, артикул+бренд и OE. Строки каталога не дублируются в этих индексах:
хранятся позиция первого представителя и признак неоднозначности.

- Индекс строится транзакциями до 1000 ключей. Для текущих 4000 входных строк
  запрашиваются только нужные ключи; RAM-карты совпадений/дублей ограничены этим
  пакетом, а не размером всего каталога.
- Дубли брендов и нормализованных артикулов блокируются по прежним правилам.
  Все строки неоднозначной пары получают прежнюю защитную метку.
- Индекс OE строится лениво при первом поиске по OE — **не раньше**, поскольку
  прежний алгоритм учитывает изменения OE, сделанные до первого fallback.
  После первого fallback индекс заморожен до конца применения, как прежний Map.
  OE нескольких разных строк считается неоднозначным, повтор одной ссылки — нет.
- Поиск связанных строк проходит те же `HVC.byArt/byOe`, с тем же порядком,
  fallback по артикулу и проверкой пустых полей, но запрашивает ключи пакетами.
  Ошибка дискового обхода останавливает Apply и запускает контрольный откат,
  а не молча пропускает связанные строки.
- Сохраняется один вектор ссылок на исходные объекты каталога (`rows.slice()`),
  чтобы дедупликация/замена массива `S.rows` не меняла смысл старого индекса.
  Это O(число товаров) ссылок, а не полный второй набор объектов или Map ключей.
- Индекс удаляется в finally. Остатки после аварии удаляются при следующем Apply
  того же источника или вместе с удалением источника. Индексы исходных конфликтов
  остаются отдельным кешем и не смешиваются с целевыми ключами.

**Это ещё не полностью дисковый целевой каталог:** `S.rows`, HVC-графы и
накопители остаются в RAM; первый пустой прайс, программные массивные импорты,
SQL и отдельные старые мастера используют прежний путь. Замена `S.rows` требует
совместимого изменения фильтров, таблицы, расчётных разделов и экспортов.

### Результаты проверок этого этапа

- `browser-catalog-lookup-indexeddb.js`: сравнение с RAM-путём на **100004**
  строках, включая точные/артикульные дубли, нормализацию, ленивый OE snapshot,
  неоднозначность, граф связанных строк и очистку аварийных индексов — PASS.
- Настоящий headless Chromium, **2 CSV × 1000 строк × 3 колонки**, полный путь
  `Import.read → mapping → Apply`: PASS. Первый прайс не наполняет HVC, второй
  файл обогащает, последний OE на месте, число SKU не растёт, экономика pending,
  undo и временный индекс очищены, сохранённый маппинг открывается повторно.
  В одном прогоне: прайс 631 мс, OE 3086 мс. Это не переносимый benchmark.
- Настоящий Chromium, **2×100000**: второй импорт не завершился за 10 минут;
  прогон остановлен. В логе первый прайс завершился, сохранение 100000 товаров
  заняло около 47 с; повторное сохранение перед вторым Apply — около 83 с,
  позднее видна запись HVC около 96 с. Полного результата и пикового RAM нет.
  **Успешного browser-прогона 2×1 млн по-прежнему нет.**
- Полный Python suite: 264 теста PASS (47.923 с); Node-регрессии и IndexedDB
  проверки PASS. Нельзя выдавать fake-indexeddb за замер скорости диска браузера.

### Запуск реального браузерного smoke-теста

```sh
npm install --prefix .arena/browser-tests playwright-core@1.58.2 @sparticuz/chromium@143.0.4 --no-save --no-audit --no-fund
NODE_PATH=.arena/browser-tests/node_modules node tests/browser-import-e2e.js
```

Нужны Linux-библиотеки Chromium (в частности NSS/NSPR). Можно указать установленный
браузер через `CHROMIUM_EXECUTABLE_PATH`. В минимальном sandbox NSS/NSPR были
распакованы из `@sparticuz/chromium/bin/al2023.tar.br` в локальный scratch-каталог,
который затем добавлен в `LD_LIBRARY_PATH`; бинарники и зависимости не входят в Git.
`E2E_ROWS` задаёт размер каждого файла, `E2E_TIMEOUT_MS` — deadline (по умолчанию
180000), `E2E_PROGRESS=1` выводит этапы. Deadline закрывает браузер, а не оставляет
долгий тест в фоне. Проверки выполняются на пустом профиле с отключёнными
автостандартными ОВХ, автопроверкой аномалий и обогащением связанных строк;
паритет связанного обхода отдельно проверен IndexedDB-тестом. Внешние ресурсы
блокируются, поэтому возможны сообщения о недоступных сетевых ресурсах/движке.

## Ожидание сохранений и точная проверка baseline

Обнаружено и исправлено: `_persistNowImpl` раньше запускал `_auxPersist()` без
`await`. Категории/HVC могли продолжать сохраняться после возврата `persistNow`,
перекрываться со следующими этапами и не входить в ожидание контрольной точки.
Теперь вспомогательные сохранения ожидаются и в успешной ветке, и после ошибки
записи товаров. Брошенная ошибка HVC сохраняется в `_hvcPersistError`; отказ
реестра без текста ошибки также не считается подтверждённым сохранением.

Перед контрольной точкой `persistNow(undefined,{verifyUnchanged:true})` может
пропустить **только запись неизменившихся товаров**:

- сверяет каждый сохраняемый объект со строкой IndexedDB по его ID, той же
  проекцией полей, что используется при записи, и `StorageCtl.same`;
- сверяет количество товаров, требует уникальные конечные числовые ID и отсутствие
  незавершённого черновика/маркеров старой записи; проверяет ревизию каталога;
- не полагается на dirty-флаг, ссылочное равенство, количество строк или хеш;
- читает до 1000 записей за раз, дополнительно держит отсортированный вектор
  ссылок на строки, а не копии всех данных;
- при несовпадении выполняет обычное полное сохранение; метаданные записывает
  даже при совпадении товаров, а категории/правила/HVC всё равно сохраняет и ждёт.

Обычные вызовы `persistNow()` и SQL сохраняют прежний выбор пути. Оптимизация
включена явно только для baseline перед безопасным браузерным Apply.

`HVC.save` больше не загружает сразу массив всех вторичных ключей, массив всех
ID и полный `Map key→id`. Удаления обходятся по первичному ключу, а сравнение и
upsert — пакетами до 1000 записей с выборкой по уникальному вторичному индексу.
Стабильные ID, пропуск неизменившихся записей и атомарность четырёх реестров с
правилами сохранены. HVC-карты в памяти приложения этим не устранены; крупные
метаданные `ozonApplicability` по-прежнему могут материализоваться целиком.

Проверки расширенного `persist-indexeddb-probe.js` (добавлен в CI): economy и
staged, 1 и 21001 товар, отсутствие product writes при совпадении baseline,

## Плотные диапазоны ключей и создание новых реестров

В real-Chromium runner добавлены замеры baseline, checkpoint, commit, source
preflight, target index и HVC-save. Checkpoint включает baseline/HVC внутри:
эти времена нельзя просто складывать.

Точечные оптимизации без смены схемы и правил сопоставления:

- Чтение ключей источника/каталога пробует ограниченный диапазон по составному
  первичному ключу. Если диапазон содержит не больше числа запрошенных ключей,
  результат полностью прочитан и фильтруется по **точному множеству** ключей.
  Если достигнут лимит N+1, используется точный bulkGet. Никакого first-match
  или предположения, что диапазон состоит только из запрошенных ключей, нет.
  Порция <=1000 запрошенных ключей, range-read <=1001 записей.
- При построении нового временного индекса ведётся максимальный уже записанный
  ключ (для целевого индекса — отдельно по виду). Только когда **все** ключи
  очередной порции строго выше этой границы, чтение прежних записей пропускается.
  Повторы внутри порции всё равно сводятся и проверяются. Любая перестановка
  назад/повтор включает обычное чтение. Граница обновляется только после
  успешного завершения транзакции.
- Если HVC-таблица изначально пуста, уникальные ключи исходного Map не могут
  ссылаться на записи предыдущих порций этого же save: для них не выполняется
  повторная выборка. При несовпадении ключа Map с ключом материализованной записи
  оптимизация отключается. Для непустого реестра остаётся прежнее сравнение,
  стабильные ID и атомарность всех четырёх реестров.

Проверки добавляют плотные, редкие переполненные диапазоны, отсутствующие ключи
и фильтрацию лишних совпадений; существующие проверки межпакетных дублей в конце
источника и OE-неоднозначности проходят. Расширенный persist probe, rollback,

## Страницы исходников вместо записи на каждую строку

Schema v3 добавляет `rowPages: [source+start],source`; существующие таблицы
не удаляются. Новые источники получают `storage: pages-v1`. Страница хранит
массив до 1000 строк и фактическую стартовую позицию. Короткие страницы на
границах CSV byte-chunk допустимы: остаток не удерживается до следующего чанка.
Поэтому память не растёт из-за ожидания «полной тысячи» длинных строк.
Буфер содержит исходные массивы ячеек, без служебного объекта на каждую строку.

Для чтения произвольного диапазона сначала ищется страница, содержащая его
начало, затем страницы до конца диапазона. Проверяются непрерывность позиций,
пустые/неправильные массивы, размер страницы, статус/счётчик источника и точное
число возвращённых строк. Вызовы маппинга, preflight, Apply и preview используют
тот же `page` API; семантика исходных значений не меняется.

Источники v1/v2 без storage-маркера либо с `rows-v1` читаются прежним способом.
Массовой миграции при старте нет. Удаление источника атомарно удаляет оба
варианта строк и все его индексы. Ошибка/отмена загрузки очищает уже записанные
страницы; сбой второй страницы отдельно проверяется тестом. Неизвестная версия
формата останавливает чтение вместо молчаливого выбора неверного декодера.

## Страницы индексов исходника и каталога (schema v4)

`keyPages` хранит до 1000 отсортированных уникальных ключей в одной записи,
адресуемой `[run+first]`, с индексом `run` для очистки. На этой схеме работают:

- сигнатуры и конфликтные бренды всего источника (`key-pages-v1` в `runs`);
- первые представители и неоднозначность целевого артикула, пары и OE
  (три независимых namespace временного каталожного run).

Для уже упорядоченного нового диапазона достаточно записать страницу. Для
произвольного порядка сначала находятся предыдущая и следующая страницы;
в пределах этого диапазона объединяются старые и входные записи. Результат
разбивается на страницы <=1000 ключей, замена выполняется одной транзакцией.
На шаг слияния материализуются не все ключи файла, а одна существующая страница
и ограниченная входная порция. Повторы внутри порции и между порциями сохраняют
накопленный признак конфликта; границы страниц не меняют решение.

Поиск группирует запрошенные ключи по страницам и возвращает только точные
совпадения. Проверяются сортировка, размер, первый ключ и отсутствие перекрытия
с соседней страницей. Если при Apply не найден ключ, который обязан входить в
полностью построенный индекс источника, операция останавливается, а не считает
его неконфликтным. Старые завершённые кеши из `keys` остаются читаемыми.

Для целевого индекса хранится исходная позиция первого представителя.
Повтор пары/артикула неоднозначен даже для одной и той же ссылки; повтор OE
одной и той же ссылки не становится ложной неоднозначностью. Снимок OE остаётся
ленивым. Поиск связанных строк и все бизнес-правила не менялись.

Очистка run/источника охватывает новый и старый форматы. Новый целевой индекс
не создаёт построчные `catalogKeys`; оставшаяся таблица нужна только для очистки
исторических временных данных. Ранее описанные high-water/dense-read оптимизации
построчных индексов теперь относятся к совместимости старого формата; новые
индексы читают и изменяют страницы.

### HVC: пакетная загрузка реестров и согласованный снимок

`HVC.load()` читает OE/parts/prices/cross по первичному `id`, порциями не более
1000 записей, вместо четырёх полных промежуточных массивов. Все четыре таблицы,
правила и справочник Ozon читаются в одной readonly-транзакции. Проверка владельца
Apply читает `meta` в той же транзакции и отклоняет незавершённый чужой импорт.
Нормализация, слияние legacy-ключей и накопление OE сохранены.

Новые карты строятся отдельно и публикуются синхронно только после успешного
чтения всего снимка. Ссылки на публичные Map сохраняются; ошибка позднего чтения
оставляет прежние карты, правила и кэши нетронутыми, выставляет ошибку загрузки
и блокирует последующее сохранение до успешной перезагрузки.

Это **не дисковый HVC**: итоговые карты остаются в RAM. При повторной загрузке
прежние карты временно сосуществуют с новыми; ограничение порции не означает
ограничения всей памяти. Пиковая память не измерялась.

Проверки этого этапа:

- `tests/hvc-stream-load-indexeddb.js`: встроенный Dexie + fake-indexeddb,
  по 3507 записей в четырёх реестрах, порции <=1000; legacy/canonical merge,
  стабильность Map, поздняя ошибка, блокировка сохранения, реальная проверка
  владельца Apply; параллельная запись не смешивает версии таблиц и правил.
- Полный Chromium Apply двух файлов по 1000 строк PASS, включая повторный
  `HVC.load()`, размеры/ссылки реестров и последнюю OE-связь; импорт без экономики.
- Node и шесть IndexedDB/probe suite PASS; Python: 264 теста, 50.410 с, PASS.
- Повтор полного Chromium Apply двух файлов по 100000 строк **не завершился**:
  deadline 360 с. Первый файл завершён за 50752 мс; второй прошёл обогащение и
  запись 100000 строк products (103858 мс), но вся операция не завершилась до
  лимита. Это не PASS и не подтверждение полного Apply 2×1 млн. Следующая цель —
  дальнейшая диагностика сохранения реестров/контрольных точек, а не увеличение
  лимита как замена исправлению.

### Apply undo: страницы вместо отдельных резервных записей

Следующий замер фаз выявил, что контрольная точка перед вторым Apply на 100000
SKU занимала 120561 мс, включая baseline-verify 4131 мс. Новый backup записывает
в `applyUndo` по одной странице на <=1000 исходных записей (`values`, `pos` —
начальная позиция), а не по одной IndexedDB-записи на каждую строку. Индексы и
версия схемы БД не меняются. Marker содержит `storage: pages-v1`, `pageSize`
и точные количества исходных строк по всем 11 таблицам.

Создание backup/marker по-прежнему одна транзакция. Восстановление проверяет
формат, размер страницы, количество страниц, точные позиции и длины, затем
восстанавливает исходные записи с прежними ключами. Очистка текущих таблиц,
replay и удаление backup/marker — одна транзакция: любая ошибка откатывает всё.
Старые контрольные точки без `storage` читаются в прежнем построчном формате.
Открывать более старую версию приложения с активной новой контрольной точкой
не следует: старый reader новый формат не понимает.

Проверено на встроенном Dexie + fake-indexeddb: 2503 products → страницы
1000/1000/503; все таблицы восстанавливаются точно; работают прежние тесты
quota/cancel, атомарного отказа restore/commit, crash/reopen/consent и защиты
другой вкладки. Добавлены восстановление legacy backup после reopen и отказ
без изменения каталога при потерянной/укороченной/смещённой странице,
неизвестном формате и недопустимом размере страницы.

Реальный Chromium, одиночные прогоны на двух файлах по 100000 строк:

- до: второй checkpoint 120561 мс (включая baseline 4131 мс);
- после: второй checkpoint 7773 мс (включая baseline 4592 мс);
- **оба прогона полного Apply INCOMPLETE**, deadline 360 с: после изменения
  второй импорт записал 100000 products за 96494 мс, затем начал `HVC.save`,
  который до deadline не завершился. Поэтому ускорение checkpoint не является
  доказательством завершения большого импорта. Следующее подтверждённое узкое
  место — сохранение HVC. Замеры фаз теперь выводятся до завершения E2E.

Полный Chromium 2×10000 PASS: price 2071 мс, OE 19413 мс, второй checkpoint
815 мс, HVC.save 11178 мс; HVC reload и последняя OE-связь проверены,
`economicsPending=true`. Node и шесть IndexedDB/probe suite PASS;
264 Python-теста PASS (49.749 с). Full Apply 2×1 млн по-прежнему не подтверждён.

### Крупные HVC-реестры: атомарные страницы в существующих таблицах

Изолированный Chromium-замер четырёх реестров по 100000 элементов подтвердил
задержку построчной записи: `HVC.save()` 342270 мс даже без Apply. Для крупных
реестров теперь используется `pages-v1`: с **20000 элементов** реестр переходит
на страницы по <=1000 логических записей. Уже переведённый реестр остаётся
страничным при уменьшении, в том числе до нуля. Малые реестры сохраняют прежний
построчный формат и стабильные первичные ID.

Страницы находятся в прежних `hvcOe/hvcParts/hvcCross/hvcPrices`: wrapper
`{id, __ucHvcPage:'v1', values}` без вторичных ключей; ключи и все поля исходных
объектов находятся внутри `values`. Физический ID wrapper — номер страницы,
а не ID отдельного элемента. Это внутренний формат: прямой вторичный запрос
`where('key')`/`where('oeNorm')` к страничному реестру больше не является API
чтения логических элементов. Приложение использует HVC.load и публичные Map;
экспорты и SQL-режим не изменены. Новая схема/версия БД не требуется.

`meta.hvcStorage` содержит формат, точное количество элементов и размер страницы
для каждого переведённого реестра. Переход с legacy, запись всех четырёх
реестров, маркера формата и правил — **одна транзакция**. Ошибка в последнем
реестре откатывает в том числе очистку старых строк и переход формата.
Неизменившаяся страница сравнивается точно и не переписывается; изменение одного
элемента переписывает только его страницу (если порядок Map не изменился).
Оставшиеся после уменьшения страницы удаляются в той же транзакции.

HVC.load читает оба формата, не более 1000 логических записей за раз. Для страниц
проверяются маркер формата, количество/номера страниц, длины, непустые уникальные
логические ключи. Неизвестный формат, пропавший marker, потерянная/укороченная
страница или дубликат останавливают загрузку без частичной публикации и блокируют
сохранение. Проверка дубликатов временно хранит Set ключей текущего реестра.
Итоговые HVC Map и S.rows по-прежнему находятся в RAM; пиковая память не измерялась.
Пакетный read сам по себе не означает ограничение всей памяти приложения.

Контрольная точка Apply сохраняет страницы как непрозрачные записи и вместе с
ними `meta.hvcStorage`; тест реального begin/save/restore/load подтверждает точное
восстановление реестров и их формата. Прежнее приложение не понимает страницы:
**не открывайте эту БД старой версией приложения**, включая случай прерванного Apply.
Откат версии требует сначала экспорта/восстановления совместимым инструментом.

### Products: ограниченная сверка первичных ключей перед записью

`saveDiffAtomic` и полная запись `saveChunked` больше не загружают все старые
первичные ключи через `toCollection().primaryKeys()` и не держат одновременно
полный Set новых ID. Используется один вектор исходных ID (без копий товаров),
сортировка по правилам IndexedDB, затем слияние с потоком старых ключей порциями
**не более 1000**. Для уже упорядоченных исходных ID сортировка пропускается;
порядок S.rows не изменяется. Старые строки целиком при сверке не читаются.
Вектор новых ID всё ещё имеет размер O(N); это не полностью дисковая операция
и не доказательство ограниченной общей/пиковой памяти.

Сравнение через `Dexie.cmp` обнаруживает и дубли составных/бинарных/date-ключей
по значению, а не по ссылке JS-объекта. Недопустимые ID и дубли отклоняются до
удаления товаров; в chunked-режиме — ещё до публикации `meta.incomplete`.
Автоматическое присвоение отсутствующих ID в обычном persist сохранено.

Удаляются только отсутствующие в новом каталоге ключи. Каждая порция удаления
<=1000 выполняется в транзакции с повторной проверкой ревизии/владельца Apply.
При `saveDiffAtomic` вложенные порции входят в общую транзакцию сохранения:
ошибка записи/отмена откатывает в том числе удаления. При `saveChunked` порции
фиксируются отдельно, как и раньше; обрыв может оставить уже удалённые строки
и маркер incomplete. **Только контрольная точка Apply обеспечивает откат всей
операции**; отдельную chunked-запись нельзя называть атомарной. Частичные
обновления changedList по-прежнему не удаляют остальные товары.

`tests/product-key-reconcile-indexeddb.js` (встроенный Dexie + fake-indexeddb)
проверяет лимит каждого primaryKeys-запроса, отсутствие чтения payload при
сверке, точное удаление/добавление разреженных и перемешанных ID, пустой каталог,
проверку дублей/невалидных ключей до изменения БД, rollback атомарной записи,
отмену между порциями, повторную проверку freshness и сохранность остальных
товаров при частичном обновлении. Тест добавлен в CI; фаза `product-keys` — в
журнал Chromium E2E.
