# Сброс соединения при HVC-обогащении большого второго файла

## Наблюдение

Первый прайс пользователя (122941 SKU) сохранён. Ошибка появляется позже:
`/catalog/enrich-hvc-rows: net::ERR_CONNECTION_RESET`, затем `TypeError: Failed to fetch`.
Это не прежняя ошибка boot и не отказы Cloudflare/favicon/source maps.
Сообщение «строки вне прайса» означает режим дозагрузки существующего ассортимента,
а не причину сетевого сбоя.

## Подтверждённый дефект транспорта

До исправления enrichHvcRows отправлял reference целиком в первой порции:
parts, oe, byArt, byOe, unsafeKeys, unsafeOe. Ограничение Handler._body — 50 МиБ.
При большой OE-базе это несовместимые требования. Сервер может отвергнуть тело,
пока клиент ещё его отправляет; тогда ошибка HTTP 413 не доходит до fetch.
Локальный запрос 51 МиБ к тому же Handler воспроизвёл
`URLError: [Errno 32] Broken pipe`.

Фактический размер графа пользователя неизвестен, лога Python-процесса нет.
Поэтому этот воспроизводимый механизм не исключает другой причины сброса,
например завершения движка или нехватки памяти.

## Исправление

- `/catalog/hvc-reference`: begin/chunk/commit/release.
- Клиент отправляет ограниченные части: не более 2000 записей и консервативной
  оценки 1 МиБ для данных части. Оценка учитывает UTF-8 без сериализации всего
  графа в одну строку; сервер независимо ограничивает данные части 2 МиБ.
- Часть сверх лимита и одна чрезмерно большая запись дают явную ошибку,
  а не попытку безразмерного запроса. Общий 50-МиБ лимит сервера НЕ повышен.
- Перед публикацией проверяются последовательность частей и общее число записей.
  После commit reference неизменяем. Пустой справочник поддерживается.
- Граф читается курсором по частям: не создаётся ещё одна полная JSON-строка графа.
- В `/catalog/enrich-hvc-rows` остаются идентификатор reference и до 1000 SKU.
  Все ответы сначала проверяются/стадируются; ошибка поздней порции не применяет
  ранние HVC-патчи к строкам. Это не обещание атомарности всего UI-импорта:
  предыдущие шаги маппинга/реестров могут уже изменить данные в памяти.
- Временный справочник освобождается при успехе или ошибке. Устаревшие загрузки
  старше суток убираются при следующем begin (в том числе после падения клиента).
- Кнопки enrichFull используют тот же пакетный маршрут и не показывают успех,
  если последующее сохранение canonical каталога не удалось.
- Сетевые ошибки показывают маршрут и предупреждение о незавершённой операции.
  Слепого повтора POST, скрытого браузерного fallback и сброса БД нет.
- В консоль добавлен отдельный замер числа записей/частей и времени передачи HVC.

## Проверки

- 234 Python-теста: OK, 56.562 с (после изменения полного HVC-пути).
- Затем усилена parity-фикстура: OE-граф, размеры, unsafe keys, нестандартный
  разделитель, три режима auto/artbrand/oe. Все 5 HVC chunk tests: OK.
- Реальный local HTTP: begin → chunk → commit → обогащение → release.
- Неполный reference запрещён; запись после commit запрещена; слишком большая
  часть не сохраняется; release удаляет данные.
- JS: граф из 55000 записей, суммарно больше 50 МиБ, отправлен за 99 частей;
  максимальный JSON-запрос 686069 байт. Команда:
  `HVC_LARGE_PROBE=1 node tests/hvc-chunked-client.js`.

- JS: ошибка второй части reference, ошибка второй порции SKU, cleanup,
  запрет успеха после отказа persist, понятная сетевая ошибка без retry.
- `node tests/run-tests.js`, py_compile, синтаксис 5 inline scripts, diff --check: OK.

## Ограничения и применение

Обновить нужно **клиент и Python-движок вместе**, затем перезапустить движок.
Новый клиент требует нового `/catalog/hvc-reference`; старый exe его не знает.
Не требуется удалять каталог или повторно загружать первый прайс, если он сохранён.
До обновления/перезапуска сохранить важные несохранённые данные из текущей вкладки.

Большой граф всё ещё требует памяти Python для HVC-расчёта. Подгрузка/построение
индексов повторяются между порциями; этот патч устраняет монолитную передачу,
но не обещает завершённую оптимизацию памяти/CPU или время на файле пользователя.
Если ERR_CONNECTION_RESET повторится, необходим вывод окна движка в момент сбоя
(особенно traceback/завершение процесса), а не только браузерный журнал.

## Последующая оптимизация: 504444 записи / 350 частей / 97830 мс

Новый журнал подтверждает завершение передачи reference (не ошибку), но не
содержит сообщения о завершении самого обогащения. Подтверждена лишняя работа:
сервер заново читал и десериализовал весь граф на каждую порцию SKU.

Изменения:
- До трёх частей reference в полёте. Номера назначаются до отправки; после
  ошибки прекращается планирование, ожидаются уже отправленные запросы и лишь
  затем выполняется cleanup. Commit — только после всех подтверждений.
- До 8000 записей в части вместо 2000, при том же консервативном byte-limit
  1 МиБ на клиенте и независимом 2-МиБ лимите данных части на сервере.
  Фактическое число частей зависит от размера записей, а не только их числа.
- Новые references индексируются в hvc_ref_entries по id/field/key при приёме.
  Значения хранятся один раз, в индексированной таблице; chunks хранит порядок
  и число исходных записей. Замена части удаляет её прежние индексные записи.
- Порция SKU читает свои byArt, соответствующие OE/byOe, доноров-держателей
  и релевантные unsafe-флаги. Порядок OE и держателей не меняется.
- В запросе явно выбран lookup-индекс: без этого SQLite предпочитал первичный
  индекс по part ради ORDER BY и повторно сканировал почти весь reference.
- References, начатые старой версией без indexed-маркера, читаются старым путём.
  Release/TTL очищают также новые индексные таблицы. Глобального безразмерного
  Python-кэша графов не добавлено.

Синтетический замер: SQLite в памяти, 504444 записи (по 126111 parts/oe/byArt/byOe,
у каждого part свой OE), порция 1000 SKU. Под tracemalloc:

| Чтение reference | Время | Пик Python-выделений | Прочитано записей |
|---|---:|---:|---:|
| Полное восстановление графа | 10,827 с | 191,98 МиБ | 504444 |
| Индексированная окрестность | 0,079 с | 1,50 МиБ | 4000 |

Сравнение — два режима чтения одного и того же подготовленного reference,
не полное время старого/нового импорта. Не включает загрузку reference,
дисковый I/O Windows, HTTP или собственно вычисления HVC. При общем OE с очень
большим числом держателей нужная окрестность тоже может быть большой.
Не обещается конкретное сокращение 97,8 секунд на устройстве пользователя.
Чтение исходного второго файла (113,4 секунды в журнале) этой правкой не изменено.

Проверки после оптимизации:
- 238 Python-тестов: OK, 46.384 с.
- Parity полного и индексированного reference: три режима, связный OE-граф,
  конфликтующие категории, размеры, unsafe-флаги, нестандартный разделитель,
  несколько порций. Ответы совпадают.
- Из 10000 нерелевантных donors тест декодирует только двух необходимых.
- Concurrency harness: максимум три запроса, уникальные номера, отсутствие
  commit после ошибки, cleanup после завершения всех уже отправленных запросов.
- Старые неиндексированные reference, реальный HTTP, staging и cleanup: OK.
- JS suite, py_compile, синтаксис 5 inline scripts и diff --check: OK.

## Следующий reset: Ozon preferred

После успешного HVC в пользовательском логе reset произошёл уже на
`/catalog/enrich-ozon-preferred`. Старый клиент отправлял полный Ozon snapshot
(включая глобальные identity rows/parts/byArt) на каждый пакет SKU; Python
заново строил модели и сохранял весь JSON при каждом запросе. Это установленный
дефект масштабирования, но без stderr Python нельзя назвать точную причину
конкретного TCP reset.

Теперь `/catalog/ozon-reference` принимает begin/chunk/commit/release.
JSON разбивается по 300000 UTF-16 code units без разрыва surrogate pair;
каждый HTTP POST ограничен размером части (даже при JSON escaping ниже 2 MiB).
SQLite проверяет непрерывность частей и полный размер перед публикацией.
Один token повторно используется всеми пакетами и post-rule проходами одного
pipeline и освобождается в finally. Незавершённые upload удаляются по TTL
24 часа при следующем begin. Повторной отправки POST и browser fallback нет.

Python хранит не более одного подготовленного Ozon справочника в process cache;
при вытеснении он восстанавливается из SQLite. Полный IdentityGuard сохраняет
межпакетное распространение unsafe OE. Это не indexed/subset Ozon: полная
модель и глобальный identity всё ещё должны помещаться в память Python;
JSON.stringify полного snapshot также всё ещё выполняется в клиенте один раз.
SQL reference хранится временно, результаты — в прежних таблицах state/products.
Старые inline API вызовы остаются совместимыми. Клиент применяет результаты
одного enrich-вызова только после проверки всех пакетов и неизменности каталога/
настроек. Это НЕ транзакция всего импорта: SQL результаты ранее успешных
пакетов могут сохраниться, если следующий пакет завершился ошибкой.

Проверки: 254 Python tests OK (45.964 s), node tests/run-tests.js OK,
6 inline scripts syntax OK, py_compile, git diff --check. Новые проверки:
actual HTTP upload/enrichment/release, паритет inline/token с глобальным
unsafe OE из другой строки, cache reuse/reload, неполный и sealed upload,
Unicode roundtrip, cleanup после ошибки и отсутствие частичной клиентской
мутации при ошибке второго пакета. Отдельный Node probe с 55000 Unicode
записями и полным JSON >50 MiB прошёл; максимальный POST 594268 bytes.
