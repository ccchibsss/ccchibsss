# 12.9.160 — индексы большого импорта без случайных вставок по ключу

## Наблюдение

Лог пользователя: первый Apply 122930 SKU — 151.9 с, из них «строки файла»
128.5 с, запись товаров 21.3 с. Следующий Apply дошёл до проверки всех 961350
строк источника; на скриншоте 528.9 с. Эта надпись не доказывает, что именно
вся длительность пришлась на один цикл: раньше таймеры начинались ПОСЛЕ
построения индексов, и экран мог оставлять последнюю надпись подготовки.

## Изменения

1. Начальные индексы источника, пары/артикула каталога и ленивого OE теперь
   строятся внешней сортировкой. Каждый блок <=1000 записей сортируется и
   сворачивается отдельно; затем стабильное 16-путевое слияние читает по одной
   странице на поток и пишет пачками до 8 страниц. Нет общего Map миллиона
   ключей и нет случайного чтения/перезаписи листа на каждый новый ключ.
   Дубликаты и конфликты объединяются через прежнюю семантику merge; первый
   представитель сохраняется в порядке исходных строк/каталога, а не сортировки.
2. Формат key-pages-v1 не меняется. Итоговые страницы плотные (до 1000 записей),
   complete публикуется только после успешной сборки. Временные серии очищаются
   при успехе/отмене/исключении. Остатки crash-серий удаляются при очистке run
   или удалении источника/старого целевого индекса.
3. Для готовых индексов хранится компактный каталог первых ключей страниц
   (одна строка на страницу, не один элемент на SKU). Точный бинарный поиск
   выбирает нужные листья; bulkGet читает до 32 страниц за запрос. Общий LRU
   ограничен 256 страницами и расчётным бюджетом 32 МиБ. Это оценка размера
   записей кэша, НЕ гарантия пикового heap всего приложения. Каталогов страниц
   удерживается не больше 8. Изменение/удаление индекса инвалидирует кэш.
   При переоткрытии сохранённого источника каталог страниц восстанавливается.
   Старые/mutable индексы остаются читаемыми с ограниченным диапазонным чтением.
4. При строгом article+brand поиске не загружается лишний article-индекс для
   строк с брендом. Строки без бренда по-прежнему используют запасной поиск.
5. Если ВСЕ неклю́чевые стандартные колонки — накопительные OE/применимость
   (или пользовательские поля), а бренд входит в ключ либо отсутствует,
   конфликт источника математически невозможен по существующим правилам.
   Отдельный проход и индекс не строятся. Цены, размеры, имя и прочие обычные
   стандартные поля, а также article-only с колонкой бренда по-прежнему требуют
   проверки ВСЕГО файла до применения первой строки. Никакой проверки только
   первых N строк нет. Сигнатура заранее исключает накопительные поля вместо
   STD.find и постоянных пустых элементов для каждой ячейки каждой строки.
   Версия fingerprint маппинга повышена, старый индекс не принимается ошибочно.
6. Таймеры начинаются перед checkpoint; в отчёте отдельно видны checkpoint,
   индекс каталога, preflight источника и подготовка. Финальное «всего» считается
   по wall time. При слиянии прогресс показывает текущий проход/группу, а не
   оставляет надпись «961350 из 961350» на всё время слияния.

Первый файл остаётся прайсом без обогащения, последующие — enrichment-only,
экономика при импорте не считается. Защита конфликтов ревизий, undo checkpoint,
rollback, нормализация и SQLite-only путь не удалены. Python/SQL не менялись.

## Безопасность текущей сессии

Не обновлять вкладку посреди Apply: исходный файл уже загружен, а часть работы
может быть в памяти/под undo checkpoint. Можно дождаться окончания или нажать
«Отменить загрузку» и дождаться завершения отмены/восстановления. Не очищать
IndexedDB. Исправления доступны после публикации версии 12.9.160; старый
запущенный JavaScript автоматически не заменится.

## Дополнение: полный лог AbortError (тот же PR #97)

Полный лог уточнил проблему: после preflight ошибка возникла в **чтении**
`keyNeighbors → lookupKeyPages → conflicts`, затем AbortError произошёл и при
автооткате `BrowserApplyCheckpoint.restore`. Это не просто долгий этап и не
CatalogConflictError из предыдущей задачи. Версия в логе — 12.9.159.
Оптимизация числа запросов не является гарантией от такого отказа IndexedDB.

Добавлено в 12.9.160:

- BrowserImportIO ограничивает повторы тремя попытками (паузы 150/300 мс).
  Повторяются только идемпотентные чтения исходных страниц/индекса/конфликтов
  либо ВСЯ прерванная атомарная транзакция восстановления. Никакого повторного
  Apply, повторного обогащения или воспроизведения уже применённой порции нет.
- Повторимы AbortError/DatabaseClosedError/InvalidStateError; видимые quota,
  конфликт ревизий, отмена, ошибки данных/схемы/безопасности не повторяются,
  включая вложенные inner/cause/failures. Нельзя установить скрытую причину
  AbortError, если сам браузер её не сообщает. Повторы ограничены и при этом.
- Используется Dexie.open, без close/deleteDatabase и без сброса токенов.
  Полное восстановление остаётся одной транзакцией, с проверкой owner и
  целостности backup на КАЖДОЙ попытке. Неуспешная попытка откатывается целиком,
  сохраняя предшествующее состояние диска и backup. Долгая/повреждённая база
  может не восстановиться и после трёх попыток — это не скрывается.
- Если все попытки отката исчерпаны, bootReady остаётся false, ошибка сохраняется,
  обычный Apply/автозапись блокируются. В маппинге есть отдельная кнопка
  «Повторить восстановление каталога». Она берёт operation lock, дожидается
  старой очереди сохранений и восстанавливает checkpoint. После успеха — reload;
  после неудачи backup не удаляется и кнопку можно использовать позже.
  Восстановление не прерывается уже выставленным флагом пользовательской отмены.
- При fault-тесте выявлен отдельный ложный детектор нумерации: одинаковые целые
  цены (77,77,...) принимались за счётчик строк и пропускались. Теперь в критерии
  считаются положительные приращения 1–2, а не нулевые. Равные цены сохраняются;
  возрастающая последовательность 1,2,3 по-прежнему распознаётся как раньше.

`tests/browser-import-abort-e2e.js` открывает настоящий Chromium с реальными
базами и прерывает транзакции через tx.abort():

### Что делать с уже упавшей 12.9.159

Не считать текущий каталог подтверждённо восстановленным: лог говорит обратное.
Не чистить IndexedDB, не удалять checkpoint и не запускать ещё один Apply.
Сохранить доступную копию памяти отдельно (она может быть частичным результатом).
После публикации новой версии открыть её и подтвердить восстановление
незавершённого импорта из checkpoint; старую вкладку с уникальными правками
не закрывать до проверки копии. Не применять новый файл до успешного
восстановления. Наличие/целостность backup именно в пользовательской БД из
лога проверить невозможно — безопасные проверки выполняются самим восстановлением.
Cloudflare rum 405/deprecated beacon не являются причиной этой цепочки ошибок.
