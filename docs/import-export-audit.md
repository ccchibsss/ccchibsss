# Аудит импорта и экспорта

Рабочая база: `0baa60c4a7b462a87b742dfebbc6dcf1dd810162` (после PR #84).
Изменения этого аудита ещё не опубликованы в main.

## Вердикт

**Нельзя считать импорт/экспорт полностью эквивалентными в browser и SQL.**
Найдены и воспроизведены дефекты, отсутствовавшие в прежних 206 тестах.
Локальные исправления перечислены ниже. Отдельно оставлены архитектурные риски:
успешные тесты не означают, что эти риски исправлены.
Причина отказа сохранения на устройстве пользователя по одному скриншоту
не установлена. Новая диагностика сохраняет исходную причину отказа.

## Повторная проверка и исправления открытых проблем

Этот раздел обновляет статус первоначальных находок ниже; исходные
воспроизведения оставлены как история аудита, а не описание текущего кода.

- **P1 exact sync исправлен:** новый `/catalog/sync` с begin/chunk/commit.
  Данные хранятся в черновике до публикации, commit под BEGIN IMMEDIATE
  проверяет SHA-256 текущих products, порядок частей, число строк и уникальность
  ключей. В одной транзакции заменяются products, очищаются старые eco_results,
  перестраивается FTS. Ошибка откатывает всё. Нули/пустые поля не проходят через
  supplier-upsert старой строки. История цен не раздувается синхронизацией.
  Устаревшие черновики удаляются через сутки. Это не меняет canonical app_catalog.
- **P1 обход маппинга исправлен для UI:** обе кнопки и PyEngine.importFile
  используют Import.pick/read/apply. В SQL parser работает на Python,
  затем общий preview/mapping/identity/quarantine/apply. Для каталогов сервер
  обнаруживает преамбулу до кэширования, возвращает порядок заголовков;
  клиент проверяет размер каждой страницы и общее число строк. Старый HTTP
  `/import/file` остаётся доступен для прямых API/фоновых клиентов, но больше
  не используется кнопками UI. XLS/ODS в SQL явно отклоняются с предложением
  сохранить XLSX; браузерная поддержка этих форматов сохранена. ZIP с несколькими
  файлами в мастере явно отклоняется вместо молчаливого выбора первого.
- **P1 fail-open Ozon исправлен:** справочник заменяется, а не накапливается;
  пустой текущий справочник очищает прежние пары. Ошибка передачи останавливает
  операцию. Перед скачиванием проверяются каталог/version, режим, настройки
  и содержимое справочника. **Это не завершает перенос всех предметных проверок
  Ozon (источники ТН ВЭД и т. п.); полного parity по-прежнему не заявляем.**
- Отрицательный/нечисловой Content-Length бинарного запроса возвращает 400.

Новые проверки: `engine/tests/test_exact_catalog_sync.py`,
`tests/import-export-fixes-client.js`. Проверены real SQLite rollback/retry,
конфликт server writer, неполные части, duplicate keys, exact zero/empty/deleted,
пустой снимок, неизменность истории, Ozon replace/clear, реальный HTTP round-trip,
SQL parser с преамбулой, клиентские partial pages и stale download.

Оставшиеся ограничения: список P2 ниже; полное Ozon parity; межклиентские
изменения normalized products **после** завершения sync и **до** отдельного
запроса recalc/export ещё не привязаны к единому server revision во всех API.
Fingerprint защищает публикацию sync, но не превращает всю последовательность
sync → recalc → download в одну серверную транзакцию. Реального файла пользователя
и Windows E2E по-прежнему нет; причина скриншота на устройстве не установлена.

## Подтверждённые и исправленные дефекты

1. **Высокий — частично записанный ZIP.** `import_rows` коммитил каждый файл,
   поэтому rollback внешнего импорта не отменял предыдущие файлы. Регрессия:
   good.csv + broken.xlsx оставляли NEW и запись истории. Добавлен параметр
   `commit=False` для частей ZIP, единый commit после rebuild FTS. Тест проверяет
   каталог и историю после поздней ошибки.
2. **Высокий — SQL enrich создавал дубль.** При нормализованном совпадении
   `AB-12/Brand` и `ab12/BRAND` INSERT использовал ключ входного файла.
   Теперь используется точный ключ существующего SKU; неоднозначный нормализованный
   ключ без точного совпадения пропускается, а не выбирается произвольно.
3. **Высокий — порча CP1251 после ASCII-префикса.** Проверялись только первые
   400 символов уже испорченной строки. Исправлено в каталожном и общем parser:
   strict UTF-8, затем strict CP1251, без silent replacement.
4. **Средний — неверный XLSX-лист.** Absolute relationship `/xl/...` превращалась
   в `xl/xl/...`, затем использовался случайный fallback-лист. Теперь путь
   нормализуется корректно. Openpyxl и stdlib используют первый лист;
   workbook закрывается в finally.
5. **Средний — пустой ZIP возвращал успех.** Архив без CSV/XLSX теперь отклоняется.
6. **Средний — общий CSV parser не учитывал quoted delimiter.** Пример:
   `article,"name;with;semicolons"` разбирался по `;`. Добавлен Sniffer;
   каталожный и общий parser поддерживают `|`.
7. **Высокий — повреждённый XLSX из-за control characters.** NUL в заголовке
   делал XML невалидным. `_xml_esc` очищает запрещённые XML 1.0 символы;
   тест разбирает все XML/rels файла и проверяет, что обычный текст `=...`
   не превращается в формулу.
8. **Высокий — CSV formula injection во вспомогательных экспортах.**
   Шаблон обогащения, комплект повторной загрузки, отчёт групп массового Ozon
   и экспорт наценок не применяли общий safeCsvText. Теперь применяют.
   JS-тест вызывает реальный downloadReimportKit и читает оба Blob.
9. **Высокий — дубли заголовков теряли данные parse/file.**
   `name;name` превращались в единственный ключ с последним значением.
   Теперь явная ошибка до создания parse_session, без молчаливой потери колонки.
10. **Диагностика/восстановление — ошибка сохранения маскировалась.**
    `persistImportOrThrow` показывает boot/volatile/IndexedDB/SQL причину.
    Исходный импорт не очищается до успешной записи. Это не устраняет
    квоту диска или недоступность хранилища на устройстве пользователя.

## Исходные открытые находки (актуальный статус — в разделе повторной проверки)

### P1. `_syncCatalog` — upsert, а не точный снимок

`PyEngine._syncCatalog` отправляет пачки `/import/rows`, но не публикует
атомарную замену normalized products. Удалённые SKU остаются; при сбое
промежуточные пачки уже записаны. Price/cost=0, volume=0, name='' сохраняют
старые значения из-за семантики import_rows (подходит для дозагрузки,
но не для точного снимка перед расчётом/экспортом).

Воспроизведение на реальном SQLite:
- seed A/B: price=100, cost=50, volume=10, name=old и второй SKU DELETED;
- import_rows A/B с price=0, cost=0, volume=0, name='';
- результат: 100/50/10/old, DELETED остаётся.

Это отдельное normalized-хранилище, **не** канонический `/app/catalog` с revision.
Выбранные export_cells ограничивают обычный экспорт, но не гарантируют
актуальность всех серверных расчётов и остальных потребителей normalized products.
Нужно отделить exact snapshot sync от импорта-обогащения и добавить revision
на все связанные расчёты/выгрузки. Нельзя просто поменять весь import_rows:
это изменит поведение импорта поставщиков и фоновых источников.

### P1. SQL-кнопка импорта обходит основной маппинг и часть проверок

`#btnImport` в SQL вызывает PyEngine.importFile, а не Import.pick/apply.
Перед отправкой `/import/file` не используются пользовательский preview/mapping
основного импорта, его source-identity/quarantine проверки и все custom-поля.
`_mergeProducts` имеет собственную семантику заполнения (в частности,
положительные размеры подставляются только в пустые). SQL parser принимает
mapping на API, но эта кнопка его не передаёт. Полный parity здесь не доказан.
Нужен единый план импорта с маппингом, проверками, явным режимом и atomic apply.

### P1. Ozon SQL export не равен браузерному валидатору

`exportOzon` сам предупреждает, что полная проверка пар/источников ТН ВЭД
остаётся в браузере. Ошибка `/ozon/pairs/import` ловится и игнорируется:
файл может строиться со старым/отсутствующим справочником. Нет защиты snapshot,
эквивалентной exportCatalogFormat, при смене каталога/настроек во время запроса.
Нужны fail-closed передача справочника, revision и общие validation fixtures.

### P2. Потенциально неожиданное расширение выборки экспорта

Exp.run при пустом фильтре может выгрузить весь разрешённый каталог с
предупреждением. Это существующее осознанное поведение, но для строгого
«выгрузить выбранное» желательно отдельное подтверждение пользователя.

### P2. Reimport-kit не является полной резервной копией

Фиксированные PRICE_KEYS/ENRICH_KEYS не содержат всех исходных и служебных
полей. Защитный апостроф CSV для значений `=.../@...` намеренно меняет
строковое представление при последующем импорте. Для точного восстановления
нужен typed snapshot/backup, а не обещание lossless round-trip этих двух CSV.

### P2. Память больших файлов

SQL export_catalog_records читает весь normalized каталог через fetchall
даже при небольшой выборке, затем собирает XML/ZIP в памяти. `_raw_table`
и CSV/XLSX parser тоже материализуют таблицы. При ошибке browser-импорта теперь
сохраняется исходный буфер для повтора, что увеличивает пик памяти до успеха.
Нужны профиль реального файла, SQL filtering до fetchall и потоковая сборка.

### P2. Политика дат Excel и числовых кодов

Первый лист унифицирован, но openpyxl возвращает Date для датных ячеек,
а stdlib reader не воспроизводит все Excel styles/serial-date правила.
Числовая ячейка с форматом `000000` сама по себе не гарантирует сохранение
отображаемых нулей при импорте. Текстовые `00042` покрыты тестами.
Нужен явный контракт по serial dates, formatted codes и формульным ячейкам
без cached value; исходные сведения не всегда восстановимы из файла.

### P2. Частные UI/HTTP риски

У нескольких отдельных кнопок async onchange/onclick нет общего error wrapper;
HTTP-обработчики бинарных файлов разбирают Content-Length до локального try.
В malformed-запросах это может давать менее понятный отказ. Это не объясняет
показанный скриншот и не исправлено предположением о причине.
