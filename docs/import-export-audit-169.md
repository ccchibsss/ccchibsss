# Импорт/экспорт: аудит производительности и памяти — 12.9.169

## Область и границы проверки

Просмотрены основные пути в `index.html` и `engine/uc_engine.py`: обычный импорт CSV/XLSX и восстановление источника, дисковый импорт, SQL parse/upload/apply, построение ключей источника и каталога/OE, обогащение и сохранение, фильтрующий Worker, CSV/XLSX каталога и Ozon, отчёт категорий, экспорт исходных данных, повторная загрузка, специализированные импорты/отчёты и Python-экспорт. Выполнен второй проход по изменённым путям и повторные проверки после исправлений.

Это аудит исходного кода и воспроизводимые синтетические тесты, **не доказательство отсутствия всех узких мест**. Файлы пользователя недоступны. Время 514 с со скриншота на конкретном файле не воспроизведено. Весь каталог по-прежнему хранится в RAM; произвольный объём данных без OOM не гарантируется.

## Что исправлено в текущей ветке

| Участок | Было | Стало / граница |
|---|---|---|
| `BrowserImportSources.buildKeyPages` | Отдельная серия на каждую страницу; async-переходы на каждый ключ; много транзакций удаления | Серии до 16 страниц / оценочных 8 MiB строк, неизменный размер листьев; I/O на границах страниц; удаление группы транзакцией. Подробности и сравнение в `enrichment-key-sort-168.md`. Один очень большой дескриптор остаётся целым. |
| `DiskXlsxWorkerMain` | Книга + полная копия AOA всех строк; все пакеты отправлялись сразу | В Worker остаётся worksheet первого листа, строки извлекаются диапазонами до 1000. Следующий пакет запрашивается только после обработки/записи предыдущего. Это **не** потоковый парсер самого ZIP/XLSX. |
| `DiskImport.eachRow` / `flush` | Цепочка записи могла накапливать готовые пакеты, пока парсер продолжал читать | CSV `onChunk` и XLSX drain ожидают `flush()` / `writeChain`. Сохраняются существующие дедупликация, HVC и атомарная подмена каталога. |
| Worker URL дискового XLSX | Blob URL скрипта не освобождался, в том числе у неиспользованной сессии | URL освобождается при завершении/ошибке/закрытии сессий; ошибка чтения файла также завершает Worker. |
| `Exp.streamXlsx` | Два параллельных AsyncZipDeflate-листа: очередь компрессора и буфер второго ZIP entry за незавершённым первым; весь архив в chunks | Последовательные ZIP entries через `BrowserExportZip`, синхронный инкрементальный deflate, OPFS; главный лист полностью закрывается до начала вводов. Нет очереди compression Workers. |
| Главный XLSX / вводы | До 4000 строк XML двух листов в parts/join за один шаг | Запись по ячейкам, строковый буфер ~256 Ki символов, сброс сжатых байтов при ~1 MiB или через 100 строк. Стили, формулы, CF и сводные листы не удалены. Добавлена проверка лимита строк/колонок. |
| `OzonReference.reportBlob` | AsyncZipDeflate, архив в RAM, XML-блоки 4000 строк | Общий последовательный ZIP/OPFS, блоки 100 строк, abort на ошибке/отмене, проверка лимита XLSX. |
| `DataOnlyExport` XLSX | Полный SheetJS worksheet и все cell objects, затем полный ZIP | Прямые XML-ячейки и последовательный ZIP/OPFS. Числа/boolean/строки сохраняют тип, строка с `=` не становится формулой; CSV-политика апострофа не переносится на исходный XLSX. Литеральные `_xNNNN_` и управляющие символы экранируются для обратимого OOXML. |
| CSV каталога, Ozon, исходных данных | Накопление всех Uint8Array/UTF-16 строк, крупные блоки 20000/3000 строк | Сброс в OPFS по ~256 Ki символов / 1000 строк, без хранения всего файла в JS при доступном OPFS. Заголовки, кодировки, BOM, quoting и CSV-защита сохранены. Одна исключительно широкая строка всё ещё временно целая. |
| Python download в браузере | `Response.blob()` как единственный путь | При доступном ReadableStream — последовательное чтение с ожиданием записи в OPFS; reader cancel/release и abort частичного файла при отказе. Совместимость с blob-only response сохранена. |
| `export_catalog_records` Python | `fetchall`, дополнительный фильтрованный список, запрос наличия export_cells и запрос snapshot на каждый товар | Один запрос метаданных + один JOIN-курсор; snapshot order и выбранные ключи сохранены. Итоговый result всё ещё список, поскольку существующий XLSX writer использует материализованные строки. |

`BrowserExportZip` не допускает открытие второго entry до закрытия первого. Ошибка записи/квоты/отмена завершают ZIP и удаляют частичный spool. При отсутствии OPFS остаётся совместимый Blob fallback, зависящий от размера файла; это **не** дисковая гарантия. OPFS имеет собственную квоту и требует свободного места. Временные файлы удаляются через 10 минут, после аварии — при следующем экспорте для собственных файлов старше суток. Новый CSV использует то же служебное хранилище; расширение его внутреннего временного файла не является именем скачивания.

## Проверки первого прохода

- Сравнение старого и нового построения индексов на 962000 случайных строках / 523170 уникальных ключах: ключи источника **47.271 → 37.663 с**, каталожные индексы **51.013 → 39.864 с**, полный индексный benchmark **117.902 → 98.146 с**. Это не полное обогащение файла. Одинаковая отсортированная последовательность lookup в обеих версиях; случайные lookup отдельно остаются в стандартном тесте.
- `browser-io-memory-e2e.js`, реальный Chromium, **20000 строк**: все распакованные XML ZIP entries общего XLSX побайтно совпали с исходным build 167; все XML отчёта категорий совпали; CSV каталога и Ozon совпали побайтно. Старые функции запускались как локальный oracle, не как production fallback.
- Новая запись общего XLSX: **3.247 с** в этом тесте. Одновременно открыт **один** ZIP entry. За тест выполнено 223 сброса, максимальный суммарный payload одного вызова sink.write **420288 байт**. Это размер сбрасываемого payload для данного теста, не общий пик RSS и не универсальный memory cap.
- Values-only XLSX перечитан настоящим SheetJS: ведущие нули, boolean, числовые значения, Unicode, переносы, формулоподобный текст, `_x0041_`, управляющий символ и пользовательские колонки сохранены. Сборка product cells через `sheet_add_aoa` в тесте запрещена.
- Проверены portable Blob fallback, ошибка квоты, abort/cleanup, отмена и отсутствие публикации частичного XLSX.
- Дисковый XLSX reader: 5000 непустых строк, 6 pull-пакетов, искусственно медленный consumer; пока consumer ожидает запись, новые строки не приходят. Сессия Worker освобождена.
- Python query-count regression: 2000 товаров, полный presentation snapshot — **два SELECT**, не тысячи; порядок snapshot, отсутствующая/пустая snapshot-таблица и фильтр ключей проверены.

## Оставшиеся узкие места — не скрывать

### P0: архитектурные ограничения на больших каталогах

1. **Резидентный каталог и реестры.** `S.rows`, `HVC.parts/byOe/oe/cross`, проекции UI/Worker, `readSqlCatalog` восстанавливают O(N) данных в браузере даже при SQLite persistence. Нужны SQL-backed paged views/search и трансформации по сессиям. Перенос только файла в OPFS не исправляет это.
2. **Атомарное Apply и результаты обогащения.** `changedRows`, staged patches, checkpoint, Ozon typing drafts и связанные enrichment-результаты могут быть O(объём изменённых данных). Нельзя просто применять ответы по мере поступления или удалять guard/rollback: потребуется протокол stage/validate/publish.
3. **Сам XLSX-парсер.** SheetJS всё ещё распаковывает и строит worksheet в Worker; передаётся полный бинарный буфер файла. `sheets:0` исключает ненужные листы, но не делает первый лист out-of-core. Нужен потоковый SAX/ZIP parser с exact typing/date/sharedStrings parity. Для очень больших источников CSV остаётся менее затратным форматом.
4. **Python generic/Ozon XLSX.** `_xlsx_from_rows`, `_xlsx_workbook`, `_ozon_rows_data`, `export_catalog_xlsx_bytes` всё ещё создают списки, XML/ZIP/BytesIO; интерфейсы byte-returning. Нужен файловый writer с курсором и теми же формулами/CF/styles. В этом изменении исправлены N+1 и browser download, а не весь server-side пик.
5. **SQL export presentation request.** `exportCatalogFormat` строит все `export_cells` и один JSON POST, сервер — весь request. Нужны сессионные порционные presentation uploads с revision checks. Значения custom/src и формулы нельзя заменить приблизительными server guesses.
6. **Dimension/OE reconciliation и расчёт.** Полные snapshot/graph JSON (`dimensionOeSnapshot`/request), сценарии и all-result Maps могут сработать после enrichment или перед расчётным экспортом. Нужны revision-pinned upload/results и отдельная атомарная публикация. Импорт не должен начать считать экономику ради оптимизации.

### P1: дополнительные расходы / специализированные пути

7. **Случайные lookup больше bounded cache.** `_keyPageCache` ограничен 32 MiB / 256 страницами. Случайные ключи каждого batch могут повторно читать почти все листья и вытеснять cache. Большие случайные probes ранее останавливались до завершения; нельзя считать это исправленным новым merge sort. Нужны дисковый merge-join или SQL lookup-сессия, сохраняя конфликтную политику.
8. **Широкие signature/ячейки.** Exact conflict signatures сохраняют все выбранные значения. Огромный OE/description/custom замедляет JSON и дисковые проходы. Замена digest требует оговорённой exact-equality стратегии, не тихого изменения сопоставления.
9. **Сводные листы высокой кардинальности.** `smallSheet` и построение категорий/тарифов всё ещё синхронные, агрегаты/сортировка могут быть O(N); «малый» лист не обязательно мал при уникальной категории на каждый SKU. Общий ZIP делает его последовательным, но отдельного async row producer здесь пока нет.
10. **Ozon калькулятор.** `generateEconomicsXlsx` сохраняет SheetJS/две AOA и unzip/repack; уже ограничен 20000 SKU. Ограничение не снято, функция не удалена.
11. **Специализированные импорты.** DictIO, тарифы, продажи/PnL, заказы, API-справочники и некоторые legacy helper readers используют `arrayBuffer`, `sheet_to_json` целого листа/всего CSV. Их нельзя считать защищёнными staging обычного Import. Нужна миграция каждого parser/mapper с собственными parity fixtures.
12. **Вспомогательные выгрузки.** `simpleXlsx`, комплекты повторной загрузки, шаблоны обогащения, отчёты цен/применимости, бэкапы/JSON, split/category exports местами держат строки/книги/массивы целиком. Они не автоматически используют новые основные streaming writers. Split ограничивает размер файла, но группировка может хранить O(N) ссылок. Нужен отдельный перевод с сохранением форматов каждого отчёта.
13. **Python upload и CSV bytes.** SQL parse публикует строки из временного spool без длинной write-lock, но HTTP body всё ещё целиком (`rfile.read`) и некоторые CSV экспорты используют `StringIO`/bytes/gzip-копию. Следующий шаг — ограниченный upload spool и file-response writers; не выдавать существующий data-only file endpoint за исправление всех endpoints.
14. **Промежуточные фильтры/индексы/дедупликация.** Выбор строк экспорта, Sets/Maps ключей, группы OE, `refreshRowRefs`, `S.view`, `idByKey`, кросс-индексы DiskImport и итоговая загрузка products_stage остаются O(N) ссылками или строками. Инкрементальные запросы требуют изменения UI-модели.
15. **Фиксированные row batches.** Транспорт SQLite persistence/enrichment ограничен числом строк, но особо широкие записи могут сделать даже 1000/5000 строк большими; JSON CPU синхронный. Лимиты по байтам/сессии нужны дополнительно, без усечения отдельных полей.
16. **Квоты и временные файлы.** OPFS/IndexedDB занимают диск, могут отказать из-за квоты, private/file контекстов или нехватки места. Много экспортов за 10 минут временно суммируются. Fallback сознательно хранит файл в памяти, а не обещает бесконечный экспорт. Отказ должен завершаться сообщением, не удалением исходной базы.

Приоритет дальнейшей работы: paged SQL-backed каталог и атомарные сессии → файловые Python export/upload → последовательный disk/SQL merge-join → специальные импорты/отчёты. Нынешние изменения закрывают конкретные лишние копии и очереди; перечисленные ограничения не объявляются устранёнными.
