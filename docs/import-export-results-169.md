# Что дали изменения 12.9.169: измерения до/после

## Краткий вывод

Главный подтверждённый выигрыш — **снижение пиков памяти экспорта**. Экспорт исходных данных в XLSX также ускорился. **Общий XLSX стал медленнее**: последовательная компрессия и запись на диск меняют скорость на меньшую память. Дисковый XLSX reader по скорости практически не изменился; выигрыш по памяти умеренный, поскольку сам SheetJS worksheet по-прежнему материализуется.

Это измерения в текущем sandbox, не на файлах пользователя и не на его компьютере.

## Методика

- До: `7c88a60f2696fa7ca94f657265d5a1f81b6d403a`, приложение 12.9.167.
- После: рабочее дерево 12.9.169, включая индексную оптимизацию 168.
- Реальный Chromium 143 (`@sparticuz/chromium@143.0.4`), Playwright Core 1.58.2, headless/single-process, Linux x86_64, OPFS доступен.
- **20000 строк, 32 пользовательские текстовые колонки** плюс стандартные поля. Строки детерминированы seed 73; Unicode и разные значения в каждой строке/колонке. Каталог уже в памяти до старта таймера.
- На каждую операцию и версию — **два отдельных свежих процесса** Chromium; порядок чередуется: до/после, затем после/до. В таблицах — медианы двух измерений (середина пары).
- Память: Node считывает `/proc/.../status` процесса Chromium и дочерних процессов каждые **25 мс**. Во всех запусках был один OS-процесс Chromium, включая Worker threads, поэтому суммирование общей памяти нескольких renderer здесь не возникает. Node/HTTP server и Python в эти цифры не входят.
- «Пик» — **максимальный пойманный RSS**, а не гарантированно истинный максимум между отсчётами. RSS включает JS, native буферы, компрессоры, Worker heaps и резервы allocator. OPFS экономит RAM, но использует диск.
- GC через CDP выполнялся после подготовки данных и после операции. Подготовка данных и последующий GC не входят во время экспорта. `peakHeapAtYields` в сырых данных — JS heap главного потока на yield/в конце, **не** непрерывный пик и **не** память Worker.
- Проверка содержимого файлов выполнена отдельным `browser-io-memory-e2e.js`: XML/CSV parity, типы, формулы и повторное чтение. В timing benchmark не включена распаковка/обратное чтение готового файла.

Два прогона дают воспроизводимый ориентир, но не полноценное статистическое исследование. Особенно небольшие различия CSV/reader нельзя выдавать за универсальное ускорение.

## Время и полный пик памяти Chromium

МиБ = 1048576 байт. Это **весь** процесс с уже загруженным каталогом, не только размер экспортного буфера.

| Операция | Время до → после | Изменение времени | Пик RSS до → после | Снижение пика |
|---|---:|---:|---:|---:|
| Общий XLSX каталога | 5.54 → 6.70 с | **на 21% медленнее** | 959 → 573 МиБ | **40%** |
| CSV каталога UTF-8 | 1.23 → 1.14 с | на 7% быстрее в этой паре, близко к разбросу | 755 → 570 МиБ | **24%** |
| XLSX «Данные без расчётов» | 9.31 → 6.01 с | **на 35% быстрее** | 1524 → 585 МиБ | **62%** |
| Дисковый XLSX reader | 4.55 → 4.54 с | **практически без изменений** | 865 → 811 МиБ | **6%** |

**Reader — только чтение/передача строк** через реальный `DiskImport._xlsxBegin().drain()`, не весь DiskImport.run с IndexedDB, дедупликацией и HVC. Все 20000 строк получены, Worker-сессия завершена. Отдельный тест backpressure использует искусственно медленного consumer; его нельзя смешивать с этим timing сравнением.

Диапазоны времени двух прогонов:

| Операция | До | После |
|---|---:|---:|
| Общий XLSX | 5.23–5.86 с | 6.64–6.77 с |
| CSV | 1.13–1.33 с | 1.09–1.20 с |
| XLSX без расчётов | 9.22–9.39 с | 5.90–6.13 с |

## Дополнительная память сверх подготовленного каталога

В начале экспортных тестов браузер уже занимал примерно 423–437 МиБ; reader начинался примерно с 436–439 МиБ. Для отделения расходов операции от исходного каталога считаем `sampled peak RSS − RSS immediately before operation` в каждом запуске, затем медиану.

| Операция | Прирост RSS до | Прирост RSS после | Снижение прироста |
|---|---:|---:|---:|
| Общий XLSX | 523 МиБ | 136 МиБ | **74%** |
| CSV | 321 МиБ | 141 МиБ | **56%** |
| XLSX без расчётов | 1089 МиБ | 149 МиБ | **86%** |
| XLSX reader | 429 МиБ | 372 МиБ | **13%** |

Снижение **дополнительной** памяти на 86% нельзя называть снижением всей памяти браузера на 86%: полный пик у этого теста снизился на 62%.

## Размер результата

| Файл | До | После |
|---|---:|---:|
| Общий XLSX | 13.99 МиБ | 14.00 МиБ |
| CSV UTF-8 | 24.53 МиБ | 24.53 МиБ |
| XLSX без расчётов | 50.70 МиБ | 14.69 МиБ |

Уменьшение последнего файла на **71%** объясняется deflate-сжатием нового writer вместо прежнего `XLSX.write` без включённой компрессии; колонки не удалялись. ZIP-байты общего XLSX слегка отличаются из-за способа компрессии, хотя распакованные XML в отдельном parity-тесте совпадают.

## Память после завершения

Retained JS heap после GC при сохранённом результате практически одинаков: около **90–91 МиБ** в экспортных случаях до и после. Постоянный каталог и его строки эта доработка не убирает.

RSS после освобождения результата не стал ниже: в экспортных случаях медианы были примерно **400–420 МиБ до** и **415–434 МиБ после**, у reader **558 → 585 МиБ**. Резервы allocator/Worker/native cache не обязаны немедленно возвращаться ОС. Эти замеры **не доказывают уменьшение idle RSS или отсутствие утечек**. Доказанный выигрыш здесь — transient peak, а не уменьшение базового каталога. Для длительного накопления нужен отдельный многоцикловый тест, а не сравнение двух свежих процессов.

## Импорт: ранее измеренное ускорение индексов

Одинаковый случайный CSV **962000 строк / 523170 уникальных ключей**, независимая проверка всех ключей и конфликтов:

| Этап | До | После | Меньше времени |
|---|---:|---:|---:|
| Индекс конфликтных ключей источника | 47.271 с | 37.663 с | **20%** |
| Каталожные индексы | 51.013 с | 39.864 с | **22%** |
| Весь индексный benchmark | 117.902 с | 98.146 с | **17%** |

Это предыдущий последовательный before/after прогон, не новые два повтора таблицы экспорта. Lookup был отсортирован одинаково в обеих версиях; большие случайные lookup с превышением cache остаются отдельным риском. Эти числа **не** означают, что полный файл обогащения пользователя теперь импортируется за 98 секунд. Пик памяти того индексного прогона не измерялся.

## Python: цена N+1 запросов

Дополнительное отдельное сравнение реальной `export_catalog_records` до/после: SQLite `:memory:`, 20000 товаров и presentation snapshot, три повторения с чередованием порядка. Результирующие строки полностью равны.

| Метрика | До | После |
|---|---:|---:|
| SELECT за один вызов | **40002** | **2** |
| Медианное время функции | **207.6 мс** | **110.0 мс** |

В этом тесте функция быстрее на **47%**. Это не полный HTTP/XLSX-экспорт. Query tracing включён в обоих случаях и добавляет накладные расходы, особенно старому N+1 пути; точный процент нельзя переносить на production без tracing. Server-side XLSX/JSON всё ещё может доминировать в полном времени и памяти.

## Практический результат

1. Наибольшая экономия памяти и одновременное ускорение — **XLSX исходных данных без расчётов**.
2. Общий XLSX стал существенно безопаснее по пикам памяти, **но медленнее** в этом тесте. Если приоритет — скорость, этот компромисс надо учитывать, а не скрывать за общим словом «ускорен».
3. CSV стал заметно легче по памяти; выигрыш времени небольшой и пока неустойчивый.
4. Дисковый XLSX reader убрал полную копию AOA/очередь пакетов, но основной worksheet SheetJS остался: поэтому общий пик снизился лишь на 6%, а не кратно.
5. Индексы импорта ускорились примерно на пятую часть; точного замера **полного** пользовательского обогащения всё ещё нет.
6. Полное устранение OOM не подтверждено: resident `S.rows`/HVC, атомарные staged results, серверные XLSX/JSON и специальные отчёты перечислены в `import-export-audit-169.md`.
