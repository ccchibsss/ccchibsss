# v12.9.58 — числовые помощники: `num()` и `round()`

Итерация к v12.9.57 (удаление ABC/XYZ). Цель — снять главную статью времени
пересчёта, найденную профилем, не меняя ни одной цифры.

## 1. Что показал профиль

`node --cpu-prof`, 20 000 строк, режим одной площадки (OZON), `runPipeline(true)`:

| Функция | Доля времени |
|---|---|
| `num()` — «число из любого поля» | **22,8 %** |
| `round()` — округление как в Excel | **19,3 %** |
| `calcMarketplacesEconomics` | 4,5 % |
| сеттер расчётного поля строки (`ROW_PROTO`) | 3,6 % |
| `finalizeMarketplaceEco` | 3,6 % |
| `computeEconomics` | 3,5 % |
| `ecoMonth`, `_expand`, GC, `normArticle`, `shareTariff`… | по 1–2,5 % |

То есть 42 % времени уходило на две функции-однострочника, которые вызываются
миллионы раз: решатель цены прогоняет десятки пробных цен на SKU, и каждая проба
пересчитывает десятки величин через `num()`/`round()`.

## 2. Что изменено

| Функция | Было | Стало |
|---|---|---|
| `num(v)` | `v === '' \|\| v == null` → `v instanceof Date` → `typeof v === 'number'` | **`typeof v === 'number'` первым**: в расчёте он и приходит почти всегда; `instanceof` (самая дорогая из проверок) выполняется только для нечисловых значений |
| `round(n, d)` | `Number(n) \|\| 0` и `10 ** d` на каждый вызов | для чисел — `(n \|\| 0)` без `Number()`; степень десяти берётся из таблицы `_POW10[0…8]`, для прочих `d` остаётся `10 ** d` |

Арифметика округления (включая правило «половина от нуля» и разбор «грязного»
произведения через `toPrecision(15)`) не тронута — это аудированная семантика
v12.9.52, сверенная с формулой `ROUND` в выгрузках.

Порядок проверок в `num()` переставлен, но набор условий тот же:
число → `isFinite ? v : 0`; `''`, `null`, `undefined` → 0; `Date` → 0; иначе
`parseFloat` с удалением пробелов и запятой → 0 при нечисле.

## 3. Дифференциальная проверка (старая vs новая реализация)

Обе версии функций взяты из файлов напрямую и сравнивались покомпонентно
(`Object.is`, включая `NaN` и `-0`):

- `num`: 20 026 значений — строки, числа, `''`, `null`, `undefined`, `NaN`, `±Infinity`,
  `Date`, `true/false`, массивы, «1 234,5», «12,34», «1e3»;
- `round`: 300 165 значений с `d = 0…6` — случайные величины в диапазоне
  ±200 000, цены с копейками, точные `.5` (включая отрицательные), «грязные»
  произведения вида `31363.499999999996`, `1e21`, строки с запятой.

**Итого 320 191 проверка — 0 расхождений.**

Микрозамер на 3 млн вызовов: `round` 250 → 127 мс (×1,97), `num` 106 → 81 мс (×1,31).

## 4. Замеры пайплайна

Стенд тот же, что в v12.9.56/v12.9.57: Node 22, клиентский скрипт в песочнице
с минимальной DOM-заглушкой, синтетический каталог, `runPipeline(true)` без записи.

**−20,7 %** времени пересчёта. В пересчёте на каталог 217 448 SKU это ≈ −96 с

### 4.2. Режим сравнения (5 площадок), 3 000 строк

14 354 мс → **12 098 мс** (−15,7 %).

Изменена себестоимость трёх строк из 2 000: пересчитано ровно 3 строки,

правка снимает время, а не память.

## 7. Что осталось в профиле

После правки `round` и `num` всё ещё занимают 32 % (18,2 % + 14,0 %): это уже
стоимость самих вызовов, а не разбора аргументов. Дальше путь один — **сокращать
число вызовов**, а не ускорять функцию:

- решатель цены (`solveMarketplacePrices` → `evaluateOzon`) прогоняет десятки пробных
  цен на каждый SKU; в режиме одной площадки пробу можно считать один раз для шага
  BE и шага целевой маржи (часть кэша уже есть в 12.9.56);
- `finalizeMarketplaceEco` + `ecoMonth` (≈7 %) считают месячные статьи для каждого
  пробного варианта, хотя в пайплайне нужен только итог базовой цены;
- сеттер поля строки `ROW_PROTO` (4,4 %) — писать расчётные поля сразу в числовой
  массив через `setRowNum` там, где индекс поля известен заранее.

Это отдельная итерация: она меняет структуру расчёта, поэтому требует такой же
построчной сверки.
