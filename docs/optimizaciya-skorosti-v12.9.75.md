# v12.9.75 — оптимизация скорости применения импорта

## Что тормозило

При применении импорта по всему каталогу (а не по загруженному файлу) выполнялись
лишние полные проходы:

1. **«OE по связке»** — `HVC.syncOeByKey()` без аргументов перебирал все SKU
   (на каждую строку: `Set`, разбор `oe_numbers`/`oe_list`, сверка с реестром),
   хотя непосредственно перед этим `HVC.rebuildIndex(S.rows)` (этап «индекс OE»)
   уже выполнил тот же sync по всему каталогу внутри себя.
2. **Группировка OE в пайплайне** — `runPipeline` при импорте вызывал
   `HVC.groupOeByKeyFromRows()` по всему каталогу даже при «малой дельте»
   (изменено < 2 % строк), хотя OE-списки неизменённых связок пересчитывать не нужно:
   они зависят только от строк своей связки «Артикул+Бренд».

## Что сделано

- Импорт: `HVC.syncOeByKey(changedList)` — синхронизируются только изменённые
  и связанные строки этого импорта. Распространение OE на остальные строки тех же
  связок выполняет группировка пайплайна.
- `HVC.groupOeByKeyFromRows(list, scope, onlyKeys)` — необязательный набор связок:
  обрабатываются только строки этих связок, чужие OE-списки не разбираются.
- `runPipeline`: при малой дельте (`deltaFast`) группировка вызывается с набором
  связок из `options.changedList`; при пустом списке — прежний полный проход
  (безопасный откат). Полные пересчёты вне импорта не затронуты.

## Замер (синтетика, настоящий код из index.html)

Каталог 200 000 строк / 50 000 связок, дельта — 100 связок:

| Проход | Было | Стало |
|---|---|---|
| Группировка OE, полный проход | 2 479 мс | — |
| Группировка OE, таргетная | — | 103 мс |

Тот же порядок выигрыша даёт точечный `syncOeByKey` на этапе «OE по связке».

## Контроль

- `tests/run-tests.js`: функциональный тест на настоящем коде — таргетная
  группировка эквивалентна полной для затронутых связок и не трогает чужие;
  статические гарантии новых вызовов.
- На реальном импорте этапы видны в консоли: `[UC] импорт: … · OE по связке … ·
  пересчёт и запись …`.
