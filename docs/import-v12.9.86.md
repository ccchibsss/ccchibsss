# v12.9.86 — Лёгкий импорт: экономика считается при экспорте

## Проблема
После импорта пайплайн сразу считал юнит-экономику по всему каталогу: на больших
прайсах это самый дорогой этап импорта и ~1,14 КБ расчётного Float64Array на
строку (из ~1,46 КБ/SKU) постоянно живого heap. При сценарии «загрузил прайс →
обогатил → сразу выгрузил» расчёт до экспорта не нужен.

## Что сделано
- Переключатель `#impLightMode` в панели импорта («Лёгкий импорт: экономику
  считать при экспорте, а не при загрузке»), настройка `S.settings.importLightMode`,
  по умолчанию выключен.
- `runPipeline(..., { skipEconomics })`: строки нормализуются, категоризируются,
  проходят политики/правила/карантин и сохраняются, но `computeEconomics` не
  вызывается и компактные расчётные массивы строк не выделяются. Каталог помечается
  `S._econPending = true`.
- `ensureEconomics()`: ленивый полный досчёт; повторные/параллельные вызовы делят
  один проход. Флаг ожидания снимает только полный расчёт (не дельта).
- Точки досчёта: экспорт (`Exp.run`, калькулятор Ozon) и вход в расчётные разделы
  через `UI.go` (Данные, Дашборд, Юнит-экономика, Экспорт, PL, Поставки, WhatIf,
  Жизненный цикл, Советник Ozon, Ограничитель цен) — с тостом «Считаю юнит-экономику».
- Отпечаток полного расчёта `uc.fullCalcFp` в лёгком режиме не пишется.

## Эффект (оценка по замерам v12.9.7-mem)
- Импорт: нет самого дорогого этапа; heap после импорта ниже на ~1,1 КБ/SKU
  (≈220 МБ на 200 тыс. SKU) до первого расчёта.
- Экспорт/первый расчётный раздел: полный проход пайплайна, как раньше.

## Проверка
- `node tests/run-tests.js` — OK (добавлены ассерты лёгкого режима).
- Стенд ensureEconomics на настоящем фрагменте приложения: досчёт при pending,
  отсутствие расчёта без pending, дедупликация параллельных вызовов — OK.
