а не недоступные исходники пользователя. Ниже отделены полный Apply,
проверка памяти процесса и точечные/составные проверки обогащения.

## 2. Память: не только performance.memory

Добавлен необязательный tests/browser-memory-probe.js. Раз в секунду Node
снимает /proc/status RSS и /proc/smaps_rollup PSS процессов Chromium, отдельно
память самого тестового Node. Через CDP Runtime.getHeapUsage измеряется V8 heap.
Сэмплер работает вне страницы и не зависит от её оценочного performance.memory.

Финальный большой прогон: около 396.5 с, 399 OS-снятий (включая диагностическое)
и 389 успешных CDP-снятий. **За весь тест, включая контрольное перечитывание
HVC после Apply:**

| Метрика | Результат |
|---|---:|
| Максимум Chromium RSS | около **1021 МиБ** |
| Максимум Chromium PSS | около **1022 МиБ** |
| Максимум JS used heap | **450.9 МиБ** |
| Heap после 5 секунд ожидания | **241.4 МиБ** |
| Heap после диагностического forced GC | **241.1 МиБ** |
| PSS после forced GC | около **719 МиБ** |
| Node RSS максимум, отдельно от Chromium | **121.1 МиБ** |

Максимумы разных метрик могут приходиться на разные секунды. Не складывать
heap + PSS: heap уже входит в память процесса. RSS может неточно обновляться
ядром; чтения RSS/PSS не атомарны, поэтому небольшое превышение PSS над RSS
здесь не свидетельствует о «памяти вне RSS». Это **наблюдённые сэмплированные
максимумы**, не гарантия, что короткий пик между снятиями был пойман.

Контрольное HVC.load после Apply само временно материализует реестры, и в этом
прогоне высокие пики были уже в области контрольного перечитывания. Поэтому
числа выше честно обозначены как пик ВСЕГО теста, а не чистого Apply. Для будущих
снятий добавлена отдельная метка verification-reopen. Большие прогоны выполнялись
до этой метки; точный чистый пик Apply из них отдельно не объявляется.

Старый performance.memory в логе сообщал 36–48 МБ в тот же большой тест. Он
может быть округлённым/устаревшим и НЕ равен памяти Chromium. В приложении слово
«кэш» заменено на **«JS heap≈ … (оценка браузера, не память процесса)»**.
Нулевое «на SKU» при отсутствии API больше не выдаётся за измерение.

**Итог:** этот сценарий не является малопамятным. Нельзя обещать работу большого
каталога на устройстве с 1 ГиБ доступной RAM. Безусловное «утечек нет» также
не подтверждено. Два полных Apply 2×1 млн и пользовательский OE-граф не проверены.

### Повторные Apply и удерживаемая память

Отдельный диагностический тест: 5000 SKU, тот же источник на 20000 строк,
4 Apply, все строки/регистры проверяются после КАЖДОГО прохода. Forced GC
вызывается только ПОСЛЕ завершённых операций, чтобы отличить мусор от удерживаемых
ссылок; он не является частью обычной работы/рекомендацией пользователю.

Удерживаемый heap после GC: **26.4 → 26.3 → 26.3 → 26.9 МиБ**.
От прогретого второго до четвёртого прохода прирост **0.56 МиБ**, а не ещё один
каталог на каждый Apply. Каталог и HVC parts/oe/cross каждый раз по 5000 записей;
undo/marker не остаются. Кэш индекса стабилен: 5 страниц, расчётно 637780 байт,
один каталог страниц. Это свидетельство отсутствия крупного линейного удержания
в этом маленьком сценарии, НЕ доказательство для любого размера/графа/браузера.
CI запускает уменьшенный вариант на 1000 SKU.

## 3. Точность: найден и исправлен реальный дефект

HVC._oeSetOf кэшировал не только общий агрегат OE, но и **список аналогов без
собственного SKU и группу со своим SKU в начале**, используя только набор OE.
Если DONOR и TARGET имели одинаковые OE, результат первого мог использоваться
для второго: TARGET получал собственный TARGET вместо DONOR в analog_list.
Ошибка воспроизводилась и в Python-реализации.

Исправлено:
- В браузере ключ кэша включает SKU+бренд, а не только набор OE. Общие дорогие
  агрегаты отдельных OE по-прежнему кэшируются отдельно; лимит кэша 4000 сохранён.
- Python сохраняет общий агрегат, но исключает собственный SKU при выдаче
  каждой строки. Хранит первые 41 кандидат, чтобы после удаления одного своего
  артикула точно получить прежний лимит 40 аналогов без повтора полного обхода
  графа на каждый SKU. Кэш ограничен 4000 наборами OE.
- Проверены разные порядки обработки трёх SKU с одинаковым OE, а также 45 SKU
  с двумя общими OE: порядок, исключение себя, лимит 40 и группа с себя в начале.
  Browser/Python результаты совпадают с независимым ожидаемым результатом.

### Полный многоколоночный Apply: RAM vs IndexedDB

Новый tests/browser-enrichment-parity-e2e.js запускает **два независимых Chromium**:
старый array/RAM lookup путь и paged IndexedDB путь текущего приложения. Это
сравнение двух путей, не запуск старой опубликованной версии 12.9.159.

Прайс 8 SKU; второй источник 4110 строк; затем ещё три файла. Сравниваются ВСЕ
выбранные поля каждой строки после каждого Apply и после переоткрытия базы.
Дополнительно проверены конкретные ожидаемые значения, а не только совпадение
двух реализаций. Путь с дисковым индексом не подменён заглушкой.

Покрыто:
- Первый прайс не обогащается; экономика не считается; 4100 строк вне прайса
  не создают новые SKU.
- Нормализованный 00-01 совпадает с 0001; source article остаётся 0001.
- Пустое значение не обнуляет цену; явное непустое обновляет её.
- Name, категория, ТН ВЭД, barcode с ведущими нулями, вес и три стороны;
  накопление всех OE A11/A12/A13 и применимости Car1/Car2; пользовательская колонка.
- Конфликт стандартного поля в повторе ПОСЛЕ границы 4000 строк блокирует ВСЕ
  варианты этого ключа, а не только позднюю строку.
- Разные бренды одного article и неоднозначный brandless lookup не выбирают
  произвольного SKU. Повтор одинаковых обычных полей с разными OE не конфликт.
- Уникальный OE переносит данные в существующую карточку, не меняя её артикул;
  неоднозначный общий OE не выбирает произвольного донора.
- TARGET получает цельный комплект 0.8/4/5/6 от донора, но сохраняет своё
  непустое название Keep и цену. Аналоги TARGET/DONOR исключают самих себя.
- Некорректный вес не заменяет прежние 0.5 кг, сохраняется причина отказа.

При сравнении исключён только volatile timestamp `at` в причине ошибки,
отсутствующий boolean трактуется как false. Остальные выбранные значения,
включая буквальное написание бренда, сравниваются. `analog_list` здесь — список
зарегистрированных держателей OE: внешний артикул FOREIGN, использованный для
сопоставления по OE, сам по себе не становится постоянным аналогом после
перестройки HVC. Сохранение всех внешних алиасов этим тестом/исправлением не
заявляется; это существующее поведение не следует путать с потерей полей SKU.

## Воспроизведение

Зависимости: как в tests/browser-import-e2e.js. На этом Linux для Chromium
потребовался LD_LIBRARY_PATH=.arena/browser-tests/libs/lib.

```
E2E_ROWS=122930 E2E_OE_ROWS=961350 E2E_TIMEOUT_MS=720000 \
E2E_MEMORY=1 E2E_MEMORY_SETTLE_MS=5000 E2E_MEMORY_GC=1 \
E2E_MEMORY_OUTPUT=/tmp/audit-memory.json \
NODE_PATH=.arena/browser-tests/node_modules node tests/browser-import-e2e.js
NODE_PATH=.arena/browser-tests/node_modules node tests/browser-enrichment-parity-e2e.js
NODE_PATH=.arena/browser-tests/node_modules node tests/browser-import-repeat-memory-e2e.js
python -m unittest discover -s engine/tests
```

Полные memory samples пишутся только в указанный внешний временный файл, не
в репозиторий. Большие входные файлы/базы не добавляются в Git.
