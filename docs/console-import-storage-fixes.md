# Разбор пользовательского лога: импорт, сохранение и экспорт (12.9.157)

## Что показывает лог, а чего он не доказывает

Первый прайс создаёт 122930 SKU; следующие файлы обогащают существующий прайс,
не создавая SKU вне него. Сообщения о пропущенных 627741/239893 строках сами по
себе не являются потерей строк каталога: это выбранная семантика текущего прайса.
Для воспроизведения именно OE-графа из лога нужны исходные файлы/настройки.
Прогоны на уникальных OE не доказывают такую же скорость на связном большом графе.

Поздний HVC.save после «мастер закрыт» и нулевое время служебных таблиц похожи
на старое не-awaited сохранение. В main после PR93 уже есть await HVC, страницы
HVC и undo. Прежний APP_VERSION не менялся между этими исправлениями, поэтому
по одной строке версии нельзя установить точный опубликованный build. Версия
поднята до **12.9.157-client+storage-export-fixes** для различения сборок.

`CatalogConflictError` нельзя безопасно «лечить» принятием текущего дискового
токена: это разрешило бы старой вкладке перезаписать чужие изменения. Причину
конкретного конфликта (другая вкладка, старый writer, восстановление и т. п.)
по присланной трассировке установить нельзя. Защита ревизии сохранена.

## Исправления текущего кода

- Большое частичное обновление (>20000 строк) раньше могло идти одной
  транзакцией даже при каталоге >20000. Теперь economy и staged отправляют его
  в saveChunked; обычные частичные обновления остаются атомарными.
- Каждая порция saveChunked теперь явная транзакция products+meta с проверкой
  свежести перед записью. Неудачная bulkPut откатывается целиком внутри порции.
  Quota, DataClone/DataError/Constraint, конфликт и пользовательская отмена не
  повторяются бессмысленно три раза. Транзитный AbortError повторяется.
  Весь chunked-save НЕ атомарный: для отката всего Apply служит undo checkpoint.
- Отказ правил/категорий/HVC теперь возвращает false из persist, сохраняет
  dirty/error/phase и не выдаёт успешный Apply. Проверка выполняется после await
  всех служебных транзакций. При конфликте/квоте не запускается ещё одна попытка
  служебных записей после отказа записи товаров. Ошибки Dexie выводятся также
  через storageErrorText, а не только как непрозрачный объект.
- MemGuard не обнуляет retry-body активного источника Apply или пайплайна.
- Для rejectLongText-колонок (нормализованные OE/группа артикулов) общий экспорт
  проверяет длину **до создания ZIP**. При превышении 32767 предлагает UTF-8 CSV.
  Согласие сохраняет длинное поле целиком; отказ не скачивает файл. CSV содержит
  значения, а не Excel-формулы/стили. Для обычных XLSX сохранён прежний путь;
  ограничение Excel не обходится повреждённым файлом и OE не обрезается молча.
  Другие форматы/экспорты этим fallback не меняются.
- Автоматическое refreshStatus в браузерном режиме не опрашивает локальный SQL
  /health; SQL-режим по-прежнему проверяет доступность движка.
- Добавлена встроенная favicon; удалены ссылки на отсутствующие source maps
  встроенных Dexie/Chart. Код библиотек не изменён.

## Внешние сообщения

`vce… Deprecated API` и `/cdn-cgi/rum` 405 соответствуют внешней аналитике
Cloudflare. В репозитории нет этого endpoint/скрипта. Проверять/отключать Web
Analytics нужно в конфигурации хостинга; подмена fetch/console ради скрытия этих
ошибок не добавлялась. `Need to reopen db` — диагностическое сообщение Dexie,
а не самостоятельное доказательство потери данных. Реальные ошибки транзакций
должны проверяться по статусу сохранения/экспорту, не игнорироваться.

## Проверки

- Node suite и console-log-regressions-client PASS: реальный _runImpl с
  подтверждением/отказом перехода в CSV; полная Unicode-строка >32767, граница
  32767; отсутствие ZIP для overflow; обычный XLSX; health и MemGuard.
- Восемь IndexedDB/probe suites PASS, включая обе ветки большого partial save,
  ошибку HVC/правил => persist false, отсутствие aux-write после конфликта,
  атомарный откат порции с уже поставленными put, transient retry и quota без retry.
- Python: 264 PASS, 53.168 с.
- Реальный Chromium: полный Apply 2×20000 PASS. Дополнительно 2×30000 PASS,
  затем persist partial 24000/30000: mode=chunked, partial=true, written=24000.
  После reopen сверены все 30000 article/cost/OE, в том числе 6000 нетронутых;
  incomplete marker удалён; economicsPending=true. Сценарий включён в CI.

Полный пользовательский набор 122930 + два крупных OE-источника в этом этапе
не воспроизводился: файлы не предоставлены. Full Apply 2×1 млн не подтверждён.
Пиковая память не измерялась, весь S.rows/HVC по-прежнему в RAM.

## Безопасное обновление

При ошибке сохранения сначала выгрузите данные из текущей памяти в CSV/JSONL.
Не очищайте IndexedDB/данные сайта. Затем, сохранив копию и закрыв другие вкладки,
обновите приложение после публикации этой версии; проверьте 12.9.157 в интерфейсе
и консоли. При предложении восстановления незавершённого Apply следуйте ему;
не принимайте новую дисковую ревизию вручную, чтобы обойти конфликт.
