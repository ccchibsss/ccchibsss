# v12.9.97 — Из плана обогащения: очередь проверки, QA, уверенность кандидатов

По итогам разбора внешнего плана построения программы обогащения каталога
внедрено то, чего в приложении не хватало (остальной план уже покрыт Каталогом V).

## Очередь ручной проверки (круг Excel)
Кнопки в разделе «Данные»: «Очередь проверки ↓» и «Решения проверки ↑».
Модуль `ReviewQueue` генерирует пары-кандидаты трёх типов:

- `oe-dims-conflict` (уверенность high) — общий OE, но разные полные габариты
  у разных связок артикул+бренд;
- `cross-dangling` (medium) — артикул из «Аналогов» отсутствует в каталоге;
- `fuzzy` (medium/low) — похожие артикулы (Левенштейн ≤ 2, блокировка
  бренд+префикс и префикс, защита от блоков-хабов >400, кап 500 пар),
  без общей OE-связи и не из списка аналогов.

Очередь скачивается CSV с пустой колонкой «Решение (принять/отклонить)».
Загрузка решений обратно: все решения запоминаются (localStorage
`uc.reviewDecisions`) и повторно не предлагаются. Применение к каталогу —
только безопасные действия: «принять» fuzzy взаимно дописывает артикулы в
«Аналоги»; «отклонить» cross-dangling убирает висячий артикул из «Аналогов».

**Правило двух ключей не нарушается**: fuzzy — только предложения оператору;
автоматический поиск и обогащение по аналогам по-прежнему запрещены.

## QA при импорте
XLSX: если ячейки артикула пришли числами, до маппинга показывается
предупреждение о возможной потере ведущих нулей (00123 → 123) — CSV читается
текстом и этой ловушки лишён.

## Проверки
- Тесты: генератор очереди на синтетическом каталоге (все три типа
  кандидатов, память решений, Левенштейн).
- Стенд полным циклом настоящим кодом: генерация → CSV решений → применение
  (аналоги дописаны взаимно, висячий кросс убран, пара не предлагается снова).
