# Проверка и ускорение Python CSV — 12.9.171-pyengine-42

> В 172 защита временно отключалась по запросу пользователя; в 173 восстановлена с тем же fast path и буферизацией. Для сохранения нулей при открытии в Excel используйте XLSX: идентификаторы записываются inlineStr, включая длинные цифровые штрихкоды. CSV сохраняет нули в файле, но не управляет автоопределением типов Excel. Апостроф ко всем артикулам не добавляется, чтобы не менять ключи загрузки Ozon.

## Результат

На 20000 товарах с длинными случайными описаниями CSV Ozon ускорился **с 3.535 до 1.865 с по медиане четырёх прогонов**: время меньше на **47%**, производительность примерно **в 1.9 раза выше**.

CSV-файл во всех восьми отдельных процессах имел одинаковые размер **23968206 байт** и SHA-256 `a2e88a4dedd7c4d99a910826b838448914fb7518ab10086d8e22e5e36b15dddc`. Ни поля, ни защита CSV, ни кодировка ради скорости не убирались.

Это сравнение **потокового CSV 170 → оптимизированного потокового CSV 171**, не старого materialized export из main 169. XLSX и импорт не ускорялись этим изменением.

## Где было узкое место

Отдельный проход до изменения, измерение через perf_counter вокруг каждого этапа, те же 20000 строк:

| Этап | Суммарное время |
|---|---:|
| Чтение SQLite + подготовка Ozon-строк | 1.438 с |
| `safe_csv_text` для всех ячеек | **1.933 с** |
| `_csv.writer` / quoting | 0.249 с |
| UTF-8 encoding | 0.029 с |
| Запись в файл | 0.074 с |

Сам stage probe добавляет накладные расходы и не равен полному timing benchmark. cProfile подтвердил направление: 920000 вызовов safe_csv_text, 2760000 re.match и 3760000 обращений к re._compile/cache за экспорт. cProfile-времена не используются для расчёта ускорения.

Одна запись на диск была не главным ограничением. Оптимизация только I/O оставляла основную стоимость защиты всех пустых/обычных ячеек.

## Изменения

1. **Буфер CSV около 65536 символов** плюс одна текущая строка: `_csv.writer` пишет строки в небольшой накопитель, затем блок кодируется и уходит в tempfile. BOM один на файл; неполный финальный блок обязательно сбрасывается. Отдельная очень широкая строка остаётся целой.
2. **Пустые ячейки** возвращаются сразу, без regex, как и раньше давая пустую строку.
3. **Обычный непустой текст/положительные числа** после обязательного удаления запрещённых control chars обходят проверки начала формулы, если первый символ не триггер и не whitespace.
4. **Триггеры и whitespace** идут через те же правила regex, заранее скомпилированные. Пробелы/NBSP/Unicode whitespace не обрезаются; точное различие Unicode whitespace и ASCII отрицательного числа сохранено. Никакого общего `strip()`/`lstrip()` вместо старой политики не используется.
5. CSV injection protection, strict CP1251 и замена ₽ в CP1251 сохранены. Файловая генерация и cleanup после ошибки кодировки сохраняются.

Эффект буферизации отдельно: до fast path два последовательных before/after прогона дали медианы **3.496 → 3.130 с** (около −10%). Это вспомогательный короткий эксперимент, не точное независимое разложение итогового выигрыша: CPU/load между сериями менялись. Основное ускорение подтверждено полным итоговым сравнением ниже.

## Итоговый benchmark

- Существующий изолированный benchmark `engine/tests/benchmark_streaming_export.py`.
- SQLite fixture с 20000 товарами. В description каждого — 32 случайных 64-битных слова, seed 73.
- По четыре свежих процесса на версию; порядок before/after и after/before чередуется каждый повтор.
- Время только генерации; подготовка fixture и последующее хеширование исключены.
- Вместо полной копии старого движка baseline — две test-only функции из 170 в `engine/tests/fixtures/csv-file-170-reference.txt`; неизменные row conversion и iterator используются из текущего engine. Эти функции не импортируются runtime-приложением. В обоих дочерних процессах baseline AST компилируется одинаково.

| Повтор | До, с | После, с |
|---|---:|---:|
| 1 | 3.448 | 1.890 |
| 2 | 3.536 | 1.839 |
| 3 | 3.572 | 1.913 |
| 4 | 3.535 | 1.841 |
| **Медиана** | **3.535** | **1.865** |

Результат относится к этому набору в sandbox; для файлов с гораздо большей долей формулоподобных/whitespace-prefixed ячеек выигрыш fast path может быть меньше. Базовая защита в этих случаях всё равно выполняется.

### Память

`resource.ru_maxrss` показал **39.5 MiB в обоих вариантах** во всех восьми процессах. Это high-water mark всей жизни процесса, включая startup/setup и возможный унаследованный floor после fork/exec. Одинаковое значение не позволяет измерить малый прирост буфера или доказать строго постоянную память; оно лишь не показывает увеличения общего измеренного пика.

Эти цифры нельзя сравнивать напрямую с 57 MiB предыдущего отчёта 170: там компилировался AST всего старого engine, здесь — только двух reference-функций. Память не «уменьшилась с 57 до 39 MiB благодаря fast path»; изменилась подготовка измерения. Файловый writer по-прежнему не удерживает CSV целиком.

## Проверки безопасности и точности

- Дифференциальное сравнение safe_csv_text с прежней реализацией: **все 65536 BMP-префиксов × 6 хвостов = 393216 случаев**.
- Дополнительные комбинации пробелов/NBSP/Unicode separators/tabs/CR/LF и триггеров.
- 10000 детерминированных случайных full-Unicode строк, scalar values, отрицательные числа, ASCII/non-ASCII digits, NaN/Infinity, control characters.
- Buffer test: 1000 строк, меньше 40 вызовов binary write вместо ~1000; верхний размер блока проверен для этой fixture, финальный остаток и число CSV-строк сохранены.
- Strict CP1251, late encoding error, закрытие tempfile, CSV/XLSX parity и реальные GET/POST endpoints остаются в регрессии.
- **274 Python tests PASS**, основной Node suite и **31 client suite PASS**, `git diff --check` PASS.

## Воспроизведение

```sh
python engine/tests/benchmark_streaming_export.py \
  --baseline engine/tests/fixtures/csv-file-170-reference.txt \
  --baseline-api file --formats csv --repeats 4 \
  --out .arena/csv-final-reference.json
```

Сохранённые сырые результаты и stage timings: `docs/benchmarks/python-csv-speed-171.json`.

Ограничения resident каталога/HVC, server-side formatted multi-sheet XLSX, больших presentation JSON и случайных disk lookup этим изменением не устранены.
