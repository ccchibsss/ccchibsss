# Повторный аудит браузер ↔ движок SQLite

## Вердикт

Полный паритет **не подтверждён**. Формулировка «сверено и совпадает» в
`audit-v12.9.155.md` для обогащения неверна. Наличие формул пяти площадок
и прохождение текущих тестов не доказывают идентичность всех веток.
Ниже — подтверждённые статическим сравнением расхождения текущего checkout.
Исправления формул в рамках этого отчёта не выполнялись.

## P0: где исполняется расчёт

`engine/uc_engine.py:recalc_catalog` загружает продукты в Python, вызывает
`_calc_all` / `calc_row`, затем записывает результат через `executemany`.
`enrich_full` строит OE-граф и выбирает доноров в Python.
SQLite сейчас хранит данные, фильтрует и агрегирует результаты, но не исполняет
все бизнес-расчёты и обогащение SQL-выражениями. Если требование — именно
исполнение SQL, а не просто отказ от браузерного вычисления, оно не выполнено.

## P1: обогащение

| Область | Браузер | Движок | Последствие |
|---|---|---|---|
| Режим поиска текста | `HVC.enrichOne`: auto сначала OE, затем artbrand; artbrand требует запись parts | `enrich_full`: всегда пара, затем OE-группа для name/applicability независимо от enrich_mode | Чужой OE-текст может попасть в режиме artbrand; в auto другой приоритет |
| Источники текста | `HVC.textFor`: OE-реестр, затем агрегат аналогов; собственные тексты SKU не используются | `frequent` по donors и products | Источник и итоговое название/применимость могут отличаться |
| Равные частоты | Порядок браузерного агрегата | `max(set(vals), key=vals.count)` | При равной частоте Python выбирает недетерминированно между процессами |
| Выбор колонок | `HVC.enCol` по каждой колонке | `enrich_full` не принимает enrichCols; HTTP вызов передаёт только два режима | Отключённые пользователем поля всё равно могут заполняться |
| Выбор ОВХ | `_enrichOneWithMode`: минимальный допустимый комплект среди снимка пары и OE-кандидата | `pair_cands` идут первыми без сортировки, затем OE | Более крупный комплект пары выигрывает у меньшего OE; результат зависит от порядка доноров |
| Проверка ОВХ | `AnomalyDetector.evaluate`, `_dimensionOeReview`, `dimensionAnomalyBlocked`; создаётся флаг проверки и provenance | `enrich_full`: только положительность и совместимость заполненных значений | Аномальный комплект может пройти; отсутствует обязательное подтверждение переноса |
| Аналоги/группа | `_oeSetOf`, `_groupOnly`, настройки колонок; присваивание рассчитанного списка | Транзитивная группа union-find; analog_list объединяется, group_articles заполняется только пустой | Семантика и повторный запуск различаются; браузерный список не просто «заполнить пустое» |

Не следует исправлять эти пункты одной заменой порядка циклов: реестр OE,
parts, прямые связи и агрегаты аналогов имеют разные роли в браузере.
Нужен эквивалентный контракт данных, а затем перенос правил выбора.

## P1: экономика

- Браузер `solveMarketplacePrices` использует `solverNetUnit`, отдельный поиск
  стабильного порога и `discontinuityAt`. Python `solve_prices` использует
  округлённый `price - total` и линейный поиск от оценки. Это разные алгоритмы;
  требуется дифференциальная проверка на тарифных порогах и дробных издержках.
  Линейный проход потенциально выполняет миллионы вычислений на SKU.
- Браузер учитывает построчный `p.wb_commission` и `p.wb_failed_cost`.
  SELECT в `recalc_catalog` эти поля не загружает. Поэтому индивидуальные
  настройки WB не могут воспроизводиться этим маршрутом.
- What-If, индивидуальные параметры ММ/Авито и кабинетные quote-ставки ЯМ
  уже исключены из снимка согласно исходному отчёту. Это ограничения паритета,
  а не подтверждённое совпадение.

## Критерии завершения исправлений

1. Зафиксировать входной контракт: OE-реестр/parts/связи, флаги колонок,
   ограничения аномалий, review/provenance, все построчные ставки и сценарии.
2. Одни и те же фикстуры исполнять в браузерном JS и серверном маршруте:
   сравнивать значения, пустые значения, списки, флаги и источники.
3. Для обогащения покрыть все комбинации режимов, конфликты и равные частоты,
   отключённые колонки, частичные ОВХ и повторный запуск.
4. Для экономики покрыть площадки/схемы/налоги, индивидуальные тарифы,
   отсутствие тарифа, 0 продаж, 100% невыкуп, пороги и минимальную целую цену.
5. Отдельно проверить, что при буквальном требовании SQL расчёт не остаётся
   Python-циклом с последующим INSERT результатов.

До выполнения этих пунктов нельзя выпускать заявление о полном паритете.

## Выполненные исправления в рабочем дереве (повторный проход)

- `enrich_cols` передаётся из клиента с учётом групповых настроек; отключённые
  поля не обновляются, счётчики названий/категорий/ОВХ учитывают отключение.
- artbrand-текст больше не использует OE-группу, auto сначала проверяет OE.
  Тексты продуктов больше не используются как донор названия/применимости.
- При равной частоте выбор детерминирован; комплекты сортируются по мере
  DimPolicy, а не по безусловному приоритету пары.
- Добавлены числовые проверки кандидата ОВХ: лимиты категории из клиента,
  нетто/брутто, плотность, конечность, явный объём и расхождение объёмов.
  Заблокированные и уже требующие review строки не получают новый комплект.
  Ответ содержит before/after; клиент создаёт `_dimensionOeReview`, источники
  и сбрасывает прежнее подтверждение аномалии.
- Индивидуальные WB/MM/Avito комиссии, расходы невыкупа, логистика ММ,
  обработка ЯМ и packCost проходят импорт, SQLite, снимок и calc_row.
  NULL означает отсутствие override, явный ноль сохраняется.
- WB-ручной расход 0 больше не заменяется расчётным расходом возврата.
- В хэш экономики добавлены transfer/agency/boost/found ЯМ и все новые
  индивидуальные поля: изменение этих входов вызывает пересчёт.

Проверки после изменений: 101 Python-тест OK, JS-тесты OK, diff --check OK.

### Ещё не закрыто

Это не полный паритет. Не перенесены целиком браузерный решатель цен с
месячным округлением, отдельный OE-реестр и граф уровней аналогов, кабинетные
quote-ставки и What-If. Проверка ОВХ покрывает числовые ограничения, но не
всю браузерную историю ошибок импорта/legacy provenance. Флаг review
применяется клиентом из ответа, но не хранится автономно движком как отдельное
состояние SKU. Полная SQL-реализация вместо Python также не выполнена.

## Следующий проход: решатель и состояние ОВХ

- `engine/price_solver.py` переносит `solveEcoInteger` и `stableFloor`.
  Дифференциальный тест извлекает действительный JS из index.html и запускает
  его в Node на 16 примерах (включая немонотонную функцию и округления).
- Модели предоставляют статьи месячных расходов; прибыль и метрика solver
  вычисляются с раздельным месячным округлением, фикс вычитается один раз.
  Транзитная упаковка и обработка объединяются, как в finalizeMarketplaceEco.
- Состояние dimension_review и dimension_context хранится в SQLite,
  синхронизируется с клиентом и возвращается в /catalog/products. Повторное
  обогащение учитывает незавершённое review и блокировку из базы, даже без
  клиентского dimension_policy. Подтверждение клиента очищает review через
  последующую полную синхронизацию.
- ALL теперь выбирает YM для основной KPI-модели вместо неявного Ozon.

Это закрывает прежние пункты о другом алгоритме поиска и об отсутствии
автономного хранения review; не является подтверждением полной эквивалентности
всех тарифных моделей. OE-граф, кабинетные quote-ставки, What-If и буквальная
SQL-реализация всей бизнес-логики остаются открытыми.

## Последний проход: тарифный контракт, сценарий, прямые OE

- Снимок ЯМ использует tariffQuoteAudit: актуальные кабинетные commission/payout,
  при stale — совместимый category fallback либо found=false. Итоговый прогноз
  невыкупа вычисляется тем же forecastNoBuyRateInfo; рассчитанное display-поле
  noBuyPct больше не ошибочно принимается за явный вход SKU. Передаётся promoCofin.
- Нулевая ставка размещения ЯМ не заменяется fallback 47%.
- `_settingsSnapshot(overrides)` / `recalcAndApply(prog, overrides)` передают
  сценарий. Сервер применяет boost/cofin/logisticsFactor к выбранной площадке,
  ymCommissionPct и targetMargin. Это контракт серверного расчёта; существующий
  интерактивный What-If UI ещё не переключён целиком на этот маршрут.
- Полное обогащение больше не использует транзитивную компоненту для текстовых
  OE-доноров: источники выбираются из прямых держателей OE. OE-реестр передаётся
  отдельно от parts, с приоритетом представителя. Первый непустой текст вместо
  наиболее частого соответствует агрегату HVC.
- Обновление списков при полном обогащении допускает замену старых значений;
  аналоги собираются из доноров, а не только из продуктов, с лимитом 40.

Проверки: 106 тестов Python OK; node tests/run-tests.js OK.

Остаточные ограничения: OE-реестр пока передаётся в запросе, не синхронизируется
как самостоятельный серверный справочник. Группа в движке пока строится от
ограниченного списка аналогов и не воспроизводит отдельные GROUP_CAP=500 и
HUB_CAP=2000 браузера. Клиентское восстановление новых строк требует отдельной
проверки всех provenance-полей. Полная SQL-реализация отсутствует: формулы всё
ещё Python. Поэтому выпускать это как полный паритет нельзя.

## Переключение обработчика и серверные справочники

Добавлена кнопка `btnProcessingMode` «Обработка: браузер / SQL» рядом с токеном
движка. По умолчанию браузер. Выбор хранится в `uc.processingMode`. Для перехода
в SQL проверяются доступность и авторизация. Смена во время ensureEconomics
блокируется, экономика помечается требующей нового расчёта. Автоматические
маршруты импорта/экспорта/расчёта используют processingAvailable, а не health.
Основные кнопки полного обогащения, OE, пересчёта, импорта и экспорта учитывают
режим. Диагностические функции движка (сверка, история, снапшоты) остаются
явно серверными. При недоступности сервера существующий браузерный fallback
сохраняется. Интерактивный What-If остаётся браузерным; переключатель не
означает, что уже перенесены все разделы приложения.

OE-реестр хранится в таблице oe_registry. Отсутствие поля в запросе использует
сохранённый справочник, явный [] очищает его. Полный снимок клиента заменяет
справочник, не оставляя удалённых OE. Группа строится отдельно от списка
40 аналогов: cap 500 и пропуск OE-хабов свыше 2000 держателей.

Проверки: 108 Python-тестов OK; JS-тесты включают реальное исполнение методов
переключателя в VM (значение по умолчанию, сохранённый режим, подпись/aria).

Режим SQL — название серверного маршрута Python + SQLite, не утверждение
о переносе формул в чистые SQL-выражения. Этот архитектурный пункт и полный
перенос What-If всё ещё не выполнены.

## Серверный интерактивный What-If и строгий выбор маршрута

Добавлен read-only `/catalog/whatif`: сравнивает одну и ту же выборку SKU,
возвращает base/scen/delta/pct/included/skipped/byCat, не перезаписывает ни
products, ни eco_results. Интерактивный WhatIf.run в режиме SQL вызывает этот
маршрут, а не цикл computeEconomics. Передаёт отдельные base/scenario настройки
и итоговые прогнозы невыкупа; проверяет отпечатки каталога, настроек и тарифов
перед публикацией. Браузерный маршрут WhatIf сохранён.

processingAvailable теперь бросает понятную ошибку при выбранном SQL и
недоступном сервере вместо false. ensureEconomics не проглатывает ошибку SQL и
не запускает runPipeline при отсутствующем результате. ensureEconomicsFor в
SQL направляется на полный серверный пересчёт вместо браузерного дельта-цикла.

Проверки: 109 Python-тестов OK, JS OK, diff --check OK. Новый тест подтверждает,
что What-If не меняет базовые результаты и входы, не считает excluded и
заблокированные SKU и возвращает ожидаемую дельту/категорийные суммы.

Вердикт остаётся: полной эквивалентности пока нет. Нужна отдельная проверка и
перенос точечного computeEconomics в карточках/сравнениях, scenarioProfit,
стандартных ОВХ-подстановок, всех правил modelReview/inputUnavailable и
неподдержанных расчётных/обогащающих разделов. Положительные тесты What-If
не доказывают полный паритет пяти моделей и всей HVC.

## Сценарий цены/продаж и временные стандартные ОВХ

`scenarioProfit` переведён в async: в SQL-режиме вызывает read-only
/catalog/whatif с отдельными price/eff_price/sales для сценария, а не
computeEconomics в браузере. Обработчик кнопки ожидает результат. Сервер
применяет сценарные входы только к копии строки.

Добавлен `_calculation_dimensions`: в расчёте используются временные ОВХ
из точного стандарта. Кандидаты собираются по виду, названию и категории;
конфликт разных комплектов между любыми кандидатами отменяет подстановку.
Существующие положительные поля не заменяются, явный объём сохраняется,
derived объём пересчитывается. Исходная строка и SQLite-продукт не изменяются.
Клиент передаёт актуальный STD_DIMS только при calcStdDims=true. В расчётный
хэш добавлены имя, вид и dimension_context.

Проверки: 111 Python-тестов OK; JS-тесты OK; diff --check OK. Новые тесты
покрывают конфликт стандартов между видом и названием, временность замены,
блокировку и неизменность исходной цены/продаж при сценарии.

Полная копия всё ещё не подтверждена: UI-детализация и части pipeline
вызывают computeEconomics синхронно; не перенесён единый полный контракт
всех UI-полей результата и всех товарных политик/автоподстановок. Этот
проход нельзя считать основанием для утверждения полного переноса.

## Общий pipeline и детализация результата

В SQL-режиме runPipeline пропускает per-row computeEconomics, ожидает
PyEngine.recalcAndApply до группировки/фильтрации/сохранения. Ошибка сервера
прерывает этот этап без браузерного экономического fallback. Категоризация,
товарные политики, правила обогащения и карантин пока остаются в клиентском
участке pipeline — это ещё не полный серверный pipeline.

Модели возвращают именованные статьи расходов. calc_row формирует fields
с unit/monthly суммами; eco_results.fields_json хранит их рядом с итогом,
/catalog/results возвращает JSON и клиент применяет его к строке. Таким
образом после серверного пересчёта не остаются старые commission/tax/logistics
и основные m*-поля от предыдущего браузерного расчёта. Версия контракта
включена в inputs_hash, чтобы старый кэш пересчитался.

Проверки: 112 тестов Python OK; JS OK; diff --check OK. Тест проверяет
сохранение детализации и согласованность месячных сумм/итога на примере Avito.
Не подтверждён полный контракт всех u*/mp/UI-полей и всех special-case
блокировок. Точечные синхронные computeEconomics в остальных разделах и
серверный перенос клиентских политик/автокатегоризации остаются открытыми.

## Новый маршрут точного HVC-контракта

Старый enrich_full не мог представить _dimensionEvidence, порядок byArt/byOe
и раздельные parts/OE. Вместо дальнейших эвристик добавлен
`engine/hvc_enrichment.py` и `/catalog/enrich-hvc`. Кнопки полного/OE
обогащения в SQLite используют новый маршрут. Клиент передаёт исходные
parts, OE, упорядоченные связи и идентификационные запреты, а не рассчитанные
обогащённые значения. Снимок сохраняется в hvc_reference и используется
автономно при последующих запросах.

Порт повторяет main/cat-проходы и auto=OE→artbrand, гейты наличия OE/пары,
приоритет OE-представителя, конфликты OE-категорий (но не выдумывает
единогласие ТН ВЭД), перенос только _dimensionEvidence, выбор минимального
OE-комплекта до проверки совместимости, review/source metadata и передачу
штрихкода/фото/кратности в допущенном main-проходе. Warranty/country не
добавляются этим маршрутом: HVC.enrichOne их не переносит. Списки строятся
из исходного графа, с браузерными caps и порядком.

`tests/hvc-reference.js` исполняет настоящий HVC из index.html в Node.
Дифференциальный тест сравнивает 18 сочетаний main/cat/column flags, включая
значения, списки, источники и review. В этих фикстурах AnomalyDetector
возвращает отсутствие issues; это не доказательство совпадения всех его
проверок. Отдельный SQLite-тест проверяет сохранение графа, источников и
идемпотентность незавершённого review.

Старые endpoints enrich_full/enrich_oe оставлены для совместимости и не
объявляются точной реализацией HVC. Новый маршрут покрывает HVC, но не
автокатегоризацию, произвольные формулы/товарные политики общего pipeline.
Поэтому утверждение о точной копии *всех* браузерных обогащений пока неверно.

## Автокатегоризация по названию: серверный маршрут

Добавлены name_category.py, лексические замены из OzonAuto._expandRaw и
/catalog/enrich-name-category. В SQL-режиме общий pipeline вызывает сервер
для NameCategory.apply и пропускает соответствующий браузерный вызов.
При дельта-проходе обрабатываются только изменённые строки. Правила получают
сырой словарь категорий/keywords, правила и множество известных голов из
справочника; выбор категории выполняется в Python. Версия словаря и
вердикт о явном источнике категории передаются из клиентского контракта.

Сравнение с настоящими NameCategory и OzonAuto в Node: 14 строк в двух
режимах (включено/выключено), включая явные категории, stale-метки,
неоднозначность, масляный насос/масло, форсунки топлива/омывателя, фильтры
и водяную помпу. Значения и метаданные совпали. Всего 116 Python-тестов OK,
JS OK, diff --check OK.

Не объявлять это полным переносом pipeline: CategoryKindAuto/OzonAuto
назначение типа/CategoryTnved, пользовательские формулы и товарные политики
ещё выполняются клиентом. Regex-оператор правил использует Python re;
полная эквивалентность всех RegExp JS (в частности Unicode/специальных
конструкций) не доказана и остаётся отдельным ограничением.
