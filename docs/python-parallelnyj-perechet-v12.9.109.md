# v12.9.109 — Параллельный пересчёт каталога на движке

Пункт 4 аудита оптимизаций (docs/python-optimizacii-v12.9.107.md).

## Что сделано

- `_calc_all(rows, st)`: чанки каталога считаются пулом процессов
  (multiprocessing.Pool, до 4 воркеров), запись в eco_results — всегда
  одним процессом через executemany. Порядок результатов Pool.map
  совпадает с порядком строк, бренд берётся из исходной строки.
- Ответ /catalog/recalc теперь содержит `parallel: true/false`;
  приложение пишет в тосте «параллельно на нескольких ядрах».
- Порог: параллелим только каталоги от 2000 SKU (на меньших накладные
  расходы пула дороже выигрыша).

## Безопасность и откат

- Любая ошибка пула → тихий откат на последовательный расчёт.
- `UC_ENGINE_NO_PARALLEL=1` — принудительно один процесс;
  `UC_ENGINE_WORKERS=N` — явное число воркеров.
- В frozen-сборке (PyInstaller) пул отключён: spawn дочерних процессов
  там ненадёжен; `freeze_support()` добавлен в точку входа на будущее.
- Та же причина не трогать: portable-сборка (embeddable pythonw + скрипт)
  пул использует штатно — проверено тестами в fork-режиме Linux.

## Проверки

- Тесты: параллельный результат равен последовательному calc_row
  (выборка 100 SKU из 2100, копейка в копейку), откат по env-флагу.
  Движок 19/19, приложение зелёные.
- Замер на 40 тыс. SKU (2 ядра песочницы): 8.2 с → 4.5 с, ×1.83,
  итоги (recalculated, avg_profit) идентичны. На 4–8 ядрах ПК
  ожидается ×3–5: пересчёт 124 тыс. — ~5–8 с вместо ~23 с.
