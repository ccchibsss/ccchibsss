# v12.9.112 — История цен и снапшоты каталога на движке

Пункт 6 аудита оптимизаций (docs/python-optimizacii-v12.9.107.md).
Не скорость, а возможность, которой в браузере не было: движок видит
каждый импорт, поэтому может помнить, как менялись цены.

## Что сделано

- Таблица price_history: import_rows сравнивает цену/себестоимость до
  upsert и пишет запись ТОЛЬКО при реальном изменении (первичная загрузка
  SKU — тоже запись, повтор без изменений — нет). Пишут все пути движка:
  импорт файла, чанки приложения, почта, папка inbox.
- GET /report/price-changes?days=N: предыдущая цена — LAG по истории;
  отдаются changed_sku, подорожало/подешевело и строки с delta_%.
- Снапшоты: POST /snapshots {note} копирует цены/себестоимость/остатки
  каталога в snapshot_rows; GET /snapshots — список; GET
  /snapshots/diff?from&to — добавленные/удалённые/изменившие цену SKU.
- Приложение: кнопки «Python: история цен» (сводка за 30 дней: сколько
  SKU подорожало/подешевело, топ-5 изменений) и «Python: снапшот цен».

## Проверки

- unittest TestHistorySnapshots: повторный импорт без изменений историю
  не плодит; подорожание +10% посчитано; дифф снапшотов — added и
  price_changed верны. Движок 26/26, приложение зелёные.
- Живой HTTP-цикл: импорт 700 → снапшот → импорт 770 + новый SKU →
  снапшот → price-changes показал +10.0%, дифф — F200 added,
  F100 700→770.

## Границы

- История начинается с установки v12.9.112: прошлых изменений движок
  не знает.
- Сравнение снапшотов в UI приложения пока одной кнопкой не выведено:
  снапшот делается из приложения, дифф — эндпоинт движка (следующий
  шаг UI при необходимости).
- Рост истории: запись на каждое изменение цены; на годы работы это
  тысячи-десятки тысяч строк — для SQLite несравнимо мало.
