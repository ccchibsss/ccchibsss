# Импорт: что оптимизировать для скорости и памяти

Аудит текущего состояния `index.html` (`APP_VERSION = 12.9.169-client`).
Вопрос владельца: «что можно оптимизировать для быстрого и качественного
импорта, чтобы память не забивалась». Ничего в коде не менялось — это разбор
с воспроизводимыми замерами.

Все числа ниже получены локально (Node 22, `--expose-gc`) на синтетике
**124 459 SKU / 42 740 строк кроссов** — том же объёме, что в
`arena-project/data.md`. Это не замеры Chromium на файлах владельца: пики
RSS/IndexedDB в браузере будут другими, но *соотношения* между вариантами
переносятся.

---

## 0. Короткий ответ

Четыре вещи дают больше всего и при этом дёшевы в реализации:

1. **`_sources` в каждой строке** — ~1 КБ из ~1,8 КБ записи, 132 МБ на диск и
   ~22 МБ heap. Происхождение полей нужно не по записи на каждую колонку, а
   на сами файлы (обычно 2–3) — строку можно свернуть без потери
   функциональности.
2. **`HVC.identityScope()` внутри `HVC.ingest()`** пересобирает identity-индекс
   по всему каталогу на каждую порцию: +617 мс на порцию 2 000 строк, ≈39 с
   лишней работы на каталог 124k. При каждом импорте, включая дисковый.
3. **Поисковая строка `_srch` (и штамп `_sv`) пишется в объект строки** и
   уезжает в IndexedDB: +337 Б heap и +166 Б записи на SKU (40 МБ heap и
   20 МБ диска впустую), при этом это чисто производное значение, которое
   пересчитывается за 160–280 мс.
4. **Контрольная точка Apply** копирует в `applyUndo` все 11 таблиц, включая
   весь каталог и все реестры, окнами по 32 строки — это тысячи транзакций и
   двойная квота на каждый импорт. Окно по байтам вместо 32 строк — правка на
   несколько строк, эффект — на порядок меньше транзакций.

Дальше по убыванию отдачи — разделы 1–8. Каждый пункт: где, что измерено,
что делать, чего нельзя ломать, как проверять.

## 1. `_sources`: 132 МБ диска и ~130 МБ JSON на каталог

**Где.** Заполняется в `Import.apply` (строка ~30740):

```js
if (previousCell !== currentCell || !p._sources[cm.srcName]) {
  p._sources[cm.srcName] = importSource; rowChanged = true;
}
```

Один и тот же объект `{file, date}` кладётся отдельно на **каждое** поле
каждой строки.

**Измерено** (`slimOf` из `_persistNowImpl`, реальная функция записи):

| Вариант строки | JSON, Б/строка | На 124 459 SKU |
|---|---:|---:|
| обычная строка после импорта (13 полей с `_sources`) | 1 834 | 220 МБ |
| из них только `_sources` | 1 111 | **132 МБ** |
| `_sources`, свёрнутый в 1–2 ссылки на файл | ~60 | ~7 МБ |
| heap, строка без `_sources` | 330 Б | 39 МБ |
| heap, строка с `_sources` (13 полей, все на один и тот же файл) | 514 Б | 61 МБ (**+22 МБ**) |

То есть примерно **60% объёма записи каталога в IndexedDB — это служебные
метаданные**, и почти всё это дубли: в замере — 13 копий одной и той же пары
`{file, date}` (по числу импортированных полей), а в файле на 201 колонку
копий будет больше.

**Что делать.**

- Хранить `_sources` в сжатом виде: либо `_sources` сведён к `['file.csv', date]`
  на уровне строки (один и тот же файл для всех полей первого прайса), либо
  отдельная таблица-интернирование: `srcId → {file, date}`, а в строке только
  `_sources: {price: 3, weight: 3, name: 4}`.
- Показывать происхождение (модалки `mgrBody`, `mpMeta`, `<div class="chips">`)
  разворачивать при открытии карточки, а не хранить развёрнутым на диске.
- Панель «Происхождение полей» уже читает `p._sources[k].file/.date` — ей нужен
  резолвер, менять её разметку не обязательно.

**Чего нельзя ломать.** `_sources` участвуют в проверках «явное значение из
файла не перезаписывается» (`_categoryNameExplicit`-подобная логика,
`CategoryKindAuto.explicitImport`, `parseDimsTriple`, `HVC.ingest` →
`_dimensionEvidence.file`), в `rowSignature`, в Ozon-доказательствах и в
`dedupeCatalog.mergeInto`. Поэтому это не «удалить поле», а «сменить форму
хранения + резолвер», с тестами на `_dimensionEvidence` и на запрет стирания
происхождения при повторном импорте того же значения
(`tests/import-export-fixes-client.js`, `tests/enrichment-*`).

**Ожидаемый эффект.** Запись каталога на диск ~220 → ~95 МБ (в ~2,3 раза
меньше объём — значит, примерно во столько же раз меньше времени на самом
«дисковом» этапе; он же главный по времени, см.
`docs/import-performance-memory-accuracy-audit.md`, где сохранение — узкое
место), плюс ~22 МБ heap. Это оценка по объёму записи, а не замер Chromium:
время IndexedDB зависит от диска, квоты и браузера, поэтому «в 2,3 раза
быстрее» здесь не утверждается.

## 2. `identityScope` в `HVC.ingest`: квадратичная работа на каждой порции

**Где.** `index.html:24193` (`const identityScope=HVC.identityScope(list)` в
начале `HVC.ingest`), `index.html:23980` (`identityScope`), `index.html:23957`
(`_buildIdentityIndex`).

```js
identityScope(list) {
  const base=this.identityCache();
  if(!list || list===base.rows)return null;
  for(const p of list) if(p && typeof p==='object' && !base.members.has(p))
    return this._buildIdentityIndex([base.rows,list]).unsafe;   // весь каталог + порция
  return null;
}
```

Дисковый импорт зовёт `HVC.ingest(part)` из `flush()` каждые 2 000 строк
(`index.html:29035`). Пока `S.rows` пуст — индекс строится по порции, дёшево.
Но после подмены каталога (`S.rows = await db.products.toArray()`,
`index.html:29124`) и на **любом** повторном импорте каждый `ingest` пересобирает
identity-индекс по всему каталогу.

**Измерено** (реальный `HVC.ingest` из `index.html`, порция 2 000 строк):

| Состояние `S.rows` | На порцию 2 000 строк |
|---|---:|
| пусто (первый импорт) | 66 мс |
| 124 459 строк (повторный импорт) | **683 мс** |

Это ≈39 с лишней работы на каталог 124k, и держится она ещё и памятью:
identity-индекс на 124 459 строк — **10,5 МБ** (две `Map` по одному и тому же
ключу: `seen` и `normalized`, `index.html:23960–23970`).

**Что делать.** Инвалидировать индекс по версии каталога (он уже так и делает),
но не пересобирать его на каждую порцию импорта:

1. Механизм дороговизны — не `identityCache` (он-то как раз кэшируется), а
   `identityScope`: порция из `flush()` состоит из **новых** объектов, которых
   нет в `base.members`, поэтому каждая порция строит объединённый индекс
   «весь каталог + порция» (`23985–23986`). Нужен отдельный флаг «идёт
   импорт»: пока он поднят, объединённый индекс не строится, а конфликты
   порции проверяются по уже существующим `parts` (см. пункт 2). Заодно
   перестанет сбрасываться и сам `identityCache` (сейчас после `S.rows.push`
   в обычном импорте меняется `rows.length`, и индекс пересобирается ещё раз).
2. Порцию, пришедшую из импорта, проверять по ней же: конфликты внутри файла
   уже ищет `BrowserImportSources.prepareKeys`/`sourceConflicts` (там для этого
   есть отдельный индекс на диске). `identityScope` для чужих объектов нужен
   только чтобы поймать конфликт «порция vs каталог» — для этого достаточно
   `parts.get(key)` + сравнение с `p.article/p.brand` (`identityUnsafe` это уже
   делает), без полной пересборки.
3. Убрать дублирующую `normalized`-`Map`: литерал можно сделать
   `a + '\u001F' + b` (нормализованные значения содержат только `[A-Z0-9А-ЯЁ]`,
   расхождений с `JSON.stringify` нет — проверено на 20 000 случайных пар),
   тогда `seen` и `normalized` — это одна структура.

**Чего нельзя ломать.** Правило «одинаковый lossy-ключ у разных литералов =
unsafe» — это защита от склейки разных SKU (`docs/import-key-index-performance.md`,
`docs/indexeddb-import-memory-174.md`). Тесты: `tests/import-enrichment-keys-client.js`,
`tests/browser-import-sources-indexeddb.js` (кросс-батчевые конфликты),
`tests/hvc-*`.

**Побочная находка.** `deleteByBrand`/`deleteByArtikul` удаляют связи по
`on + '|' + k` (`index.html:25020, 25033`), а создаются они по
`on + '\u001F' + k` (`index.html:24260, 24473`). Разбор — в разделе 5.

## 3. `_srch`/`_sv`: производное поле живёт в записи и на диске

**Где.** `ensureSrch()` (`index.html:22316`) пишет `p._srch` и `p._sv` прямо в
строку; `matchFilterRow` читает `p._srch` (`index.html:22168`).

**Измерено:**

| Метрика | Значение |
|---|---:|
| heap на `_srch` + `_sv`, 124 459 SKU | **+337 Б/SKU, +40 МБ** |
| JSON записи с `_srch`/`_sv` vs без | 465 Б vs 299 Б → **+19,7 МБ диска** |
| построение при `bumpVersion` | 163 мс первый раз, ~120 мс повторно (инкрементально по `_sv`) |

`slimOf` (`index.html:23008`) вырезает только `_t, _bw, id, mp, _stdDimsCalc`,
поэтому `_srch` и `_sv` уходят в IndexedDB. При загрузке (`loadAll`) они
приезжают обратно, но `_srchVer` сбрасывается — и строки всё равно
пересчитываются.

**Что делать.** Не хранить `_srch` в объекте строки: держать её в
`WeakMap(row → string)` (или в `Map` по `id`), сбрасывать при `bumpVersion`
и строить лениво только когда в фильтре появился непустой `q`. Сейчас строка
строится даже при пустом поиске. `FWorker` строит свою копию `_srch` сам —
там ничего менять не нужно.

**Проверка.** `tests/run-tests.js` не покрывает поиск; нужен маленький клиентский
тест: `matchFilterRow` с `q` возвращает те же строки при хранении в `WeakMap`,
а запись в IndexedDB не содержит поля `_srch` (это легко проверить через
`persist-indexeddb-probe.js`).

## 4. Дисковый импорт: убрать лишние полные записи каталога

**Где.** `DiskImport._runInner` (`index.html:29098–29137`).

Сейчас после потоковой записи в `products_stage` выполняется:

1. транзакция подмены: `products.clear()` + перекладывание всех строк
   из `products_stage` в `products` через **Dexie-запросы** (`limit(2500)`,
   `bulkDelete` по id) внутри одной большой транзакции — `index.html:29100–29118`;
2. `S.rows = await db.products.toArray()` — весь каталог в память
   (`index.html:29124`);
3. `runPipeline(..., { persist:false })` — пересчёт;
4. **снова** `db.products.bulkPut` по 2 500 строк (`index.html:29134`);
5. `HVC.save()` — реестры (`index.html:29135`).

То есть каталог за один импорт перезаписывается **дважды** (черновик → каталог
→ каталог после пересчёта), а на пике одновременно живут: черновик на диске,
каталог на диске, полный `S.rows` в памяти и `slimBack`-копия порциями.

**Что делать (по убыванию эффекта).**

- **Убрать шаг 4.** Пайплайн в режиме `skipEconomics` меняет у строк
  `article_norm`, `oe_norm`, `group_articles`, `groupSize`, `_srch`, `excluded`
  и т.п. Если писать только эти изменения — получится один `bulkPut` по
  дельте (или вообще отказаться от них в дисковом режиме: они выводятся при
  загрузке). Сейчас это вторая полная запись на 124k строк.
- **Подмену каталога делать не «через чтение-перекладывание», а на уровне
  хранилищ.** `products_stage` — тот же формат, что `products` (`'++id'`,
  `docs/…`); после успешной потоковой записи можно `products.clear()` и
  переносить пачками в отдельных коротких транзакциях с маркером
  `stageOwner`, как это уже делает `saveChunked`. Одна транзакция на 124k
  строк — это большой clone-буфер и AbortError-риск ровно там, где сейчас
  худшее место.
- **Читать каталог страницами, а не одним `toArray()`.** `db.products.toArray()`
  (`29124`) отдаёт один массив всех строк сразу — Dexie читает всю таблицу и
  держит промежуточные результаты, а `S.rows.forEach(codeFieldsToStr)`
  (`29125`) проходит по нему ещё раз. Постраничное чтение (например, по
  `PAGE_BYTES`-бюджету, как в checkpoint) даёт тот же `S.rows`, но без пика
  «все строки сразу + копия результата внутри Dexie». Заодно это позволит
  пропустить шаг 4 для строк, которые пайплайн не изменил (см. ниже).
- **Не пересчитывать OE-индекс по всему каталогу при пустом реестре.**
  В `runPipeline` `HVC.groupOeByKeyFromRows`/`rebuildIndex` идут по `S.rows`;
  в дисковом импорте кроссы уже собраны в `crossByPair` — их можно загрузить в
  реестр и не повторять полный проход (сейчас `HVC.ingest(part)` делается
  на каждом flush, плюс полный `rebuildIndex` в пайплайне).

**Ожидаемый эффект.** Один полный проход записи вместо двух — это примерно
вдвое меньше времени на «дисковом» этапе и меньше пик по памяти (нет
одновременной `slimBack`-копии + `toArray()`).

## 5. `HVC.cross`: объект-значение на каждую связку

**Где.** `index.html:24262`: `HVC.cross.set(ck, { oeNorm: on, artKey: key })`;
формат сохранения — отдельная таблица `hvcCross` (`index.html:25206`).

**Измерено** на 400 000 связок:

| Значение | Память |
|---|---:|
| `{oeNorm, artKey}` | 195 Б/запись (74 МБ) |
| константа (ключ уже содержит оба поля) | 131 Б/запись (50 МБ) |

Экономия ~**40 МБ** на плотном графе. Ключ — `oeNorm + '\u001F' + artKey`, то
значение дублирует его целиком.

**Что делать.** Значение → константа/`1`; `oeNorm` и `artKey` восстанавливать
из ключа (`split('\u001F')`), ровно как это уже сделано при чтении
(`index.html:25308–25310`). Точки чтения значения: `index.html:46520`
(`HVC.cross.get(entry.linkKey)` → `.oeNorm`), выгрузка реестров
(`index.html:25051, 25206`). Тест — `tests/hvc-chunked-client.js`,
`tests/hvc-pages-indexeddb.js` (там сверяется содержимое реестров),
`tests/hvc-reference.js`.

**Там же — реальный баг разделителя.** Запись и чтение используют `'\u001F'`
(`index.html:24260`, `25313`, `46520`), а два места удаления — `'|'`:

```js
HVC.cross.delete(on + '|' + k);   // index.html:25020 и 25033
```

Это `deleteByBrand`/`deleteByArtikul` («Управление данными», кнопки
`index.html:49248, 49262`). Эффект: `byArt`/`byOe` чистятся, а строки `cross`
остаются, и следующий `HVC.save()` (`index.html:25140`, выгрузка `25051`)
записывает их обратно в `hvcCross` — то есть ровно то, от чего предупреждает
комментарий на `index.html:49250–49251` («иначе после F5 кросс-ссылки-сироты
возвращались из Dexie»). На корректность подстановки габаритов это не влияет
(`DimPolicy.live` дополнительно проверяет `HVC.parts.get(partKey)`,
`index.html:46520–46522`), но растёт реестр и его запись; при удалении бренда
это все связки всех его OE. Фикс — `HVC.cross.delete(on + '\u001F' + k)`.

**Побочно.** `oe`-реестр держит `dimensions_str` (ещё одна копия строки габаритов
на каждый OE) — стоит проверить, не выводится ли поле из `length/width/height`.
`byArt`/`byOe` — `Map<string, Set<string>>`; на 400 000 связок это ещё
~30–40 МБ, и оба множества дублируют то, что уже выводимо из `cross`. Если
`cross` станет константой, `byArt`/`byOe` остаются единственным местом, где
связи хранятся структурно, — их надо оставить (по ним идёт обход
`29527`, `31110`, `46380`), а вот `cross` можно перестать держать в памяти
целиком: он нужен только для `size` и для `get` по одной связке.

## 6. Контрольная точка Apply копирует весь каталог и все реестры

**Где.** `BrowserApplyCheckpoint` (`index.html:29206–29315`), вызов —
`index.html:30304` (`checkpoint = await BrowserApplyCheckpoint.begin()` в начале
`Import.apply`).

Перед каждым применением файла делается полная резервная копия:

1. `persistNow(undefined, {verifyUnchanged:true})` — базовое сохранение
   (`29246`);
2. маркер в `meta` (`29252–29256`);
3. **последовательное копирование 11 таблиц** — `products`, `products_stage`,
   `meta`, `cats`, `rules`, `excs`, `imports`, `hvcOe`, `hvcParts`, `hvcCross`,
   `hvcPrices` (`29217`, `29258–29276`) в `applyUndo` страницами ≤512 КиБ.

Окно чтения — **32 строки** (`limit(32)`, `29268`), и каждая порция идёт
отдельной `rw`-транзакцией с `assertCatalogFresh()` внутри (`29263–29266`).
`pages()` группирует по `PAGE_BYTES`, но при окне в 32 строки группа почти
никогда не набирается.

**Что это стоит.** Каталог 124 459 строк: `124 459 / 32 ≈ 3 900` транзакций
только на `products`, плюс по одной на каждые 32 записи каждого реестра
(для файла кроссов в 42 740 строк это ещё ≈1 300 на `hvcCross` и т. д.).
Объём `applyUndo` при этом ≈ полный размер `products` + всех реестров, то есть
копия большей части базы и примерно двойная квота на время импорта. И платится
это на **каждом** Apply — `begin()` вызывается до проверки колонок
(`index.html:30304`), то есть даже когда файл приносит 10 строк.

Замеров Chromium здесь нет: цифры — арифметика по коду (окно 32 строки,
`PAGE_BYTES` 512 КиБ, ~1,8 КБ на строку).

**Что делать (по возрастанию риска).**

- **Окно чтения — по байтам, а не по 32 строки.** Читать `limit(500)` или
  наполнять окно до `PAGE_BYTES`; тогда `pages()` наконец начинает работать,
  а транзакций становится в ~15 раз меньше при том же объёме страниц.
  Это чистая локальная правка, риск почти нулевой.
- **Не копировать `products_stage` и `imports`** — это производные/журнальные
  таблицы, восстановимые без потери данных (`products_stage` вообще
  перезаписывается импортом). Экономия — размер источника.
- **Реестры `hvc*` копировать поколениями, а не строками.** `HVC.savePaged`
  уже пишет неизменяемые страницы с указателем поколения (`docs/
  import-index-recovery-175.md`); откат может вернуть указатель на прежнее
  поколение вместо копирования 400k строк в `applyUndo`.
- **Радикальнее:** `products` тоже пишется поколениями (`StorageCtl.productBatches`,
  `saveChunked`). Тогда «откат» — это возврат указателя, а `applyUndo` нужен
  только для `meta/cats/rules/excs` (мелкие таблицы).

**Чего нельзя ломать.** Гарантию «прерванный импорт не оставляет каталог
в полуизменённом состоянии» и восстановление после перезагрузки
(`restoreAtomic`, `29320`; тест `tests/browser-apply-checkpoint-indexeddb.js`
и раздел про откат в `tests/browser-import-sources-indexeddb.js`).
Поэтому это не «убрать копию», а «копировать
дешевле»: маркер, порядок публикации и проверки `assertCatalogFresh`
обязаны остаться.

## 8. Скорость и качество: не «память», но прямо влияет на импорт

- **Два полных прохода по источнику в `Import.apply`.** Сначала
  `BrowserImportSources.prepareKeys` строит индекс ключей (`index.html:29912`):
  страницы источника читаются целиком (`29929–29935`), и на **каждую** строку
  вызывается `describe` → `importDataSignature` → `JSON.stringify`
  (`index.html:30430–30442`, `30446`). Потом чанками по 4 000 строк идёт сам
  apply (`index.html:30473`) — ещё один полный проход по тем же страницам.
  Сигнатура нужна только при реальном повторе ключа (расчёт внутри ветки
  `else`, `30461–30463`), а `describe` считает её всегда.
  Смягчает: при совпадении fingerprint (тот же файл и та же раскладка колонок)
  `prepareKeys` возвращает кэш и первого прохода нет (`29914–29925`). То есть
  цена платится на первой загрузке файла и при смене раскладки — но именно
  тогда, когда и так тяжело.
  **Что делать.** Считать сигнатуру лениво: в `describe` вернуть только ключ,
  а сигнатуру считать во втором проходе для тех ключей, которые уже
  встречались (их список — `sourceVariants`/`sourceConflicts`). Порядок
  величины: ~200 мс и десятки МБ мусора на 124k строк — того же порядка, что
  и `JSON.stringify(row)` в разделе 7.
- **Определение кодировки CSV смотрит только первые 400 символов**
  (`index.html:28785`, и та же эвристика в `index.html:25742, 37567, 40644,
  44979`; в `index.html:31188` похожее место — `BrowserImportSources.prepare`).
  Воспроизведено на синтетическом CP1251-файле: шапка на латинице, 7 строк
  артикул+бренд+коды, первый не-ASCII байт — с позиции 614;
  кириллицы в первых 400 символах нет → эвристика возвращает `utf-8`, и строка
  `Z1;BOSCH;Фильтр масляный;777` декодируется как
  `Z1;BOSCH;������ ��������;777`. Предупреждения нет — это именно *качество
  импорта* (и «кракозябры» попадают в `name`, а затем в поиск и выгрузку).
  Проверять надо весь уже прочитанный 64 КиБ-пробник: если в нём есть
  `\uFFFD` при utf-8, а при CP1251 — нет, брать CP1251. Плюс давать
  пользователю выбор кодировки в окне импорта.
- **XLSX читается через `file.arrayBuffer()`** (`index.html:28876` в
  `BrowserSourceXlsxWorker`, `29695` в `DiskXlsxWorkerMain`, и ещё
  `31184`, `34615`, `36807` для ручных XLSX-загрузчиков) —
  книга целиком уходит в память главного потока, а затем в воркер. «Потоковым»
  остаётся только разбор; ввод-вывод — нет. Для файлов на сотни мегабайт это
  главный пик. Частичное решение: не копировать буфер в главном потоке
  (`file.slice` + transfer по частям невозможен для ZIP без распаковки, но
  можно сразу отдавать `File` в воркер — `File` structured-clone'ится без
  копирования содержимого).
- **В SQL-режиме кнопка «Прайс + кроссы — сразу в приложение» отключается
  молча:** `DiskImport.pick()` первой же строкой уходит в `Import.pick()`
  (`index.html:28902`), хотя подпись кнопки обещает дисковый поток. Пользователь
  не понимает, почему поведение другое. Стоит писать это в подсказке кнопки в
  зависимости от режима (дисковый поток — только для browser-режима).

## Как воспроизвести замеры

Все числа получены одноразовыми скриптами на Node без зависимостей
(`--expose-gc`, `process.memoryUsage()`, `hrtime`); формы строк повторяют
`arena-project/data.md`. Замеры `HVC.ingest` используют **реальный** код
`HVC` из `index.html`, вырезанный в `vm`-контекст вместе с `normArticle`,
`codeList`, `OE_DELIMITERS` — то есть измеряется прод-функция, а не её модель.
Это по-прежнему синтетика: пользовательские CSV недоступны, поэтому
утверждения о пиках RSS/памяти браузера здесь не делаются.

Что именно замерено, а что выведено из кода:

- **замерено на реальном коде из `index.html`:** `HVC.ingest` на порции 2 000
  строк (66 мс против 683 мс), `slimOf` на 5 000 строк (1 834 Б/запись,
  `_sources` 1 111 Б), размеры `_srch`/`_sv` и `_sources` в heap (Node 22,
  `--expose-gc`), байты JSON на добавочные поля (`salesSeries`, `oe_list`,
  `oe_norm`), `JSON.stringify` против обхода без склейки, детектор кодировки
  на синтетическом CP1251-файле;
- **выведено из кода, без замера:** число транзакций checkpoint и источников
  (арифметика по окну 32 строки / 512 КиБ), цена второго прохода Apply,
  сироты в `HVC.cross` после `deleteByBrand` (видно по несовпадению
  разделителя в `set` и `delete`).
